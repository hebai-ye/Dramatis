## 一、这一版要回答的三个问题

1. **账号是什么？** 要不要邮箱、手机号、第三方登录？
2. **后端放哪儿？** 自建、托管服务，还是先不建？
3. **加密做到哪一步？** 服务端能不能看见明文——如果能，这个功能就不该做。

## 二、硬约束（先摆出来，后面所有方案都要过这几关）

| # | 约束 | 出处 |
| --- | --- | --- |
| 1 | **本地库是唯一真相源**，断网、服务端下线都不影响使用 | DESIGN §8.1 |
| 2 | **后端不接触明文对话与 API Key**，端到端加密不是可选项 | DESIGN §8.3 / ROADMAP P2-7 |
| 3 | 后端**不代理模型请求**，流量由客户端直连服务商 | DESIGN §8.3 |
| 4 | 实体带 `uuid` + `updatedAt` + `deletedAt`，服务端分配单调递增 `rev` | DESIGN §8.2 |
| 5 | 消息顺序不能只靠时间戳：`(deviceId, localSeq)` | ROADMAP P2-6 |
| 6 | 同一账号下要能区分设备，用于同步诊断与冲突定位 | ROADMAP P2-5 |
| 7 | 角色状态冲突用 LWW；**冲突的记忆全部保留** | DESIGN §8.2 |
| 8 | 项目定位是 BYOK 自用与小圈子分享：**不能要求用户先注册邮箱再来聊天** | README 定位 |

约束 2 是这一版的分水岭：**服务端只应看到密文与坐标**。任何需要服务端读懂内容的方案
（服务端检索、服务端合并、服务端生成）一律出局，不管它多方便。

## 三、候选方案

### 3.1 账号形态

| 方案 | 用户要做什么 | 服务端知道什么 | 结论 |
| --- | --- | --- | --- |
| **A. 同步空间 + 同步密码**（客户端生成空间 ID，密码派生密钥） | 记一个同步密码（或存一份恢复码） | 空间 ID、凭证哈希、密文、时间 | ✅ **采用** |
| B. 邮箱 + 魔法链接 | 邮箱、点链接 | 邮箱、登录时间、密文 | ⬜ 备选（若将来要「找回」） |
| C. 第三方 OAuth（GitHub/Google） | 授权 | 第三方身份、密文 | ❌ 把「聊天记录」和实名社交身份绑在一起，用户会犹豫；也与「不注册也能用」冲突 |
| D. 手机号 | 短信验证 | 手机号 | ❌ 成本与合规都最重，收益为零 |

**为什么是 A**：它和 BYOK 的定位一致——**你带自己的钥匙，我们不带你的身份**。
用户不需要交出任何身份信息，服务端拿到的是一个随机空间 ID 与一堆密文。

#### 3.1 修订（2026-09-19，用户提出）：用户 id 由用户自己填

原方案里空间 ID 是**客户端随机生成**的。用户提出改成：**用户自己输入一个 id**
（可以填手机号），**不需要验证码**，**密码由用户手动设置**。这条已采纳，
下面是它改了什么、代价是什么。

| 项 | 原方案 | 修订后 |
| --- | --- | --- |
| 空间标识 | 客户端随机 UUID | **用户自己想一个 id**（手机号、邮箱、昵称都行），先到先得 |
| 验证 | 无 | 仍然无：不验证手机号，也不验证邮箱——它就只是个名字 |
| 密码 | 用户设，PBKDF2 派生 | 不变 |
| 服务端看到什么 | 随机 id | **用户填的那个 id 本身**（下面说明怎么缓解） |

**怎么落地（P2-6 实现这个协议时照这个写）**：

1. 客户端把用户输入的 id **规范化**（去空白、大小写折叠），算一个 `spaceHandle`，
   服务端只认 `spaceHandle`。默认用 **PBKDF2-SHA256（迭代 100k，salt 固定串）**
   而不是裸 SHA-256——它挡不住针对手机号段的定向爆破，但把「拖库之后一眼看出
   谁是谁」变成「得跑一遍字典」。
2. 与同步密码的分工不变：`spaceHandle` 决定「同步哪一堆密文」，
   同步密码派生 `authKey`（凭证）与 `encKey`（加密）。密码错就是解不开。
3. **id 占用是公开信息**：服务端不可避免地会暴露「这个 id 已经被占了」。
   这与原方案的「服务端什么都不知道」有差距，所以界面上必须写清楚
   「你填的 id 服务端看得见，介意就填个化名，别填手机号」。
4. 恢复码与「忘了密码只能靠封存文件」两条不变。

**为什么不干脆保留随机 id**：用户自己填的 id 才记得住，换台设备不用先找恢复码。
这是拿一点隐私换可用性，代价写在上面第 3 条，由用户自己选（界面上给提示）。

代价要写清楚：

- **没有「忘记密码」**。密码丢了，服务端也解不开（这正是 E2E 的含义）。
  所以：① 建空间时**强制显示一次恢复码**（32 字节随机，等价凭证）；
  ② 界面上写明「忘了密码就只能靠封存文件」——而封存（P2-4）已经做完并验证过了。
- 弱密码会被离线爆破（服务端手里有密文）。所以：客户端用 **PBKDF2-SHA256 600k 迭代**
  派生密钥；界面给出强度提示；恢复码是真正的兜底。

### 3.2 后端形态

| 方案 | 部署门槛 | 成本 | 与约束 2 的关系 | 结论 |
| --- | --- | --- | --- | --- |
| **A. Cloudflare Worker + D1**（自建，附参考实现） | 需要一个 Cloudflare 账号 + 一条命令 | 免费额度覆盖个人使用 | 只存密文，天然满足 | ✅ **采用（参考实现）** |
| B. Supabase | 注册即可，有现成托管 | 免费档够用 | 只存密文；但它自带邮箱账号体系，会诱导我们放弃方案 3.1-A | ⬜ 备选 |
| C. Firebase | 注册即可 | 免费档够用 | 同上，且离线同步模型与我们的本地优先不完全贴合 | ⬜ 备选 |
| D. 自建 VPS + 一个 Node 服务 | 买机器、配域名、看证书、担运维 | 有固定成本 | 满足 | ❌ 为了同步一个自用项目去当运维，不划算 |
| E. 用私有 Git 仓库当存储 | 无 | 无 | 满足 | ❌ 仓库体积与提交频率都不适合聊天记录，且会污染提交历史 |
| F. 先不做后端：只做「同一台机器上的文件夹同步」 | 无 | 无 | 满足 | ❌ 解决不了「手机接着聊」这个原始需求 |

**采用 A 的关键点：协议先行。** 客户端只认一个 **endpoint + 空间凭证**，
后端是可替换的：

```
POST /spaces/{spaceId}/push   推本地新记录
GET  /spaces/{spaceId}/pull?since={rev}   拉别人的新记录
GET  /spaces/{spaceId}/head   只问「现在到哪个 rev 了」
```

于是：官方给一份**一条命令部署**的 Cloudflare Worker（`deploy/cloudflare/`，P2-6 时写）；
愿意自建的人照着协议实现；不愿意自建又不想用 Cloudflare 的人，等 Supabase 适配。
**客户端不绑死任何一家**——这是把「运维负担」和「用户选择」分开的唯一办法。

### 3.3 加密与鉴权

```
同步密码 / 恢复码 ──PBKDF2-SHA256(salt=spaceHandle|用途, 600k)──┬─→ authKey ─ HMAC ─→ 凭证（Bearer）
                                                               └─→ KEK（只用来包/解主密钥）

随机主密钥 encKey ──┬── KEK(密码) 包一份 ──→ 服务端
                    └── KEK(恢复码) 包一份 ──→ 服务端
                    └── AES-GCM ──────────→ 记录密文（服务端只看到这个）
```

**实现后的修正（P2-6 第二步，2026-09-19）**：原方案写的是「密码派生出的第二半直接当
`encKey`」。真去写的时候发现这句话和 §3.1 的「恢复码等价于凭证」**互相矛盾**：密码与
恢复码是两个不同的字符串，各自派生出的 `encKey` 也必然不同——用恢复码登录进来，
只会看到一堆解不开的密文。

所以改成**随机主密钥 + 两份额外封装**：建空间时生成一个 256 bit 的随机 `encKey`，
分别用「密码派生的 KEK」与「恢复码派生的 KEK」各包一份，两份都存服务端；谁登录成功
谁就解开**同一个**主密钥。服务端因此多存两个字段（两份封装——密码一份、恢复码一份），
以及两个凭证哈希（两个凭证等价，都能过鉴权）。它仍然看不到明文，也解不开封装：
KEK 由用户密码派生，服务端手里没有密码。

| 用途分开 | 盐里带 `password` / `recovery`，所以「拿恢复码那份封装去当密码那份解」会直接失败 |
| --- | --- |
| 封装算法 | AES-256-GCM（WebCrypto 的 `wrapKey` / `unwrapKey`），AAD 绑 `purpose|spaceHandle` |
| 主密钥 | 解出来是**不可导出**的，只活在当前会话内存里 |

| 项 | 做法 |
| --- | --- |
| 加密算法 | **AES-256-GCM**（WebCrypto 原生，浏览器与 Node 都有） |
| 附加数据（AAD） | `spaceHandle \| collection \| id \| updatedAt`——把密文绑死在它的坐标上，防止服务端把 A 的记录挪到 B 上、或用旧版本顶新版本（§4.4） |
| 服务端存的凭证 | `SHA-256(凭证)`，不存明文；凭证本身是 HMAC 输出（256 bit 随机），拖库也无法反推 |
| 服务端存的记录 | `spaceHandle, collection, id, rev, ciphertext, iv, updatedAt(明文，用于 LWW 诊断), size` |
| 服务端存的空间 | `spaceHandle`、**两份凭证哈希**（密码的、恢复码的）、**两份主密钥封装**（同上） |
| 不存的 | 对话内容、角色设定、记忆、API Key、邮箱、手机号、IP 之外的任何身份信息 |
| 传输 | 一律 HTTPS；`Authorization: Bearer <凭证>` |

**为什么 `updatedAt` 可以明文**：LWW 需要它，而「这条记录在第几毫秒被改过」泄露的信息
可以忽略。要是连它都不想给，可以退化成「全部按服务端 rev 排序」——代价是设备时钟乱时
冲突判定会退化，实施时再决定。

**单条记录太大怎么办**：一条记录 = 一个实体（一张卡、一条消息、一条记忆），
按平台请求/行大小上限切块，块与块之间用同一个 `id` + `part` 编号。

## 四、同步协议草案（P2-6 照着这个写）

### 4.1 同步单位

**每实体一条记录**，不是整体快照。理由：

- 增量：两台设备各自离线聊十轮，联网后只推各自那十条，不重传历史
- 断点续传：移动网络断在中途，下次接着推没推完的那几条
- 冲突：冲突范围收敛到单个实体（一条记忆、一个角色状态），不会因为「快照对快照」而全丢

**同步白名单**（第一批）：`rooms`、`conversations`、`scenes`、`instances`、`cards`、
`worldBooks`、`messages`、`memories`、`chapterSummaries`、`personas`。

**不同步**：

| 集合 | 为什么不 |
| --- | --- |
| `usageRecords` | 账单是**本地事实**：两台设备各调各的模型、各花各的钱，合并会重复计数 |
| `backgroundTasks` | 队列是设备本地的执行状态，同步它只会让两台设备抢同一件事 |
| `meta` 里的 `schema.version` / `session.lastRoomId` | 前者是本机库的状态，后者的「最后打开」本来就该按设备算 |
| API Key | 约束 2：永不离开设备（DESIGN §8.3） |

### 4.2 冲突与顺序

| 对象 | 策略 | 理由 |
| --- | --- | --- |
| 角色状态、关系、情绪 | **LWW**（比 `updatedAt`，平局比 `deviceId`） | 慢变量，谁最后改谁算 |
| 记忆 | **全留**（不同 id 就是两条） | 多记一点用户能接受，丢一条他会发现 |
| 消息 | **append-only + `(deviceId, localSeq)` 排序** | 两端离线各聊一段，合并后仍然稳定；时间戳会因为设备时钟而错乱 |
| 场景、对话、世界书 | LWW | 同角色状态 |
| 删除 | 软删除（`deletedAt`），同步墓碑 | 直接删的话，另一台设备下次同步会把这条「又推回来」 |

### 4.3 拉取循环

```
本地游标 rev = 上次拉到的服务端 rev
1. POST push：把本地 updatedAt > 上次推送点的记录推上去（带 baseRev，服务端决定新 rev）
2. GET pull?since=rev：拿到别人改过的记录 → 解密 → 按上表合并 → 更新游标
3. 记录本地「推送点」，避免重复推
```

每次同步都是**幂等**的：push 同一条记录两次，服务端只是把 rev 推到更新；
合并同一批记录两次，结果不变。

### 4.4 写加密工具时发现的协议空隙 ✅ 已定（2026-09-19，方案 A）

**问题**：AAD 里带着 `rev`（`spaceHandle|collection|id|rev`），可 §4.3 又说
「rev 由服务端分配」。这两句话放在一起是做不到的——**客户端加密时还不知道服务端会给
哪个 rev**，等它知道了，密文已经封好了。真按这个写，第二台设备拉下来的时候，
它手里只有服务端给的 rev，而密文是按另一个 rev 加的，AAD 对不上，一条都解不开。

根子是同一个词被当成两件事用：**「这条记录改到第几版了」（客户端知道）** 与
**「服务端把它排在第几号」（服务端知道）**。

两个候选方案，**采用 A，并且已经实现**：

**方案 A（已采用）：AAD 改用 `updatedAt`，并让每条记录的 `updatedAt` 严格递增。**

```
spaceHandle|collection|id|updatedAt
```

- 仓储层写入时盖章：新时间若不比这条记录上一次的 `updatedAt` 晚，就取「上一次 + 1ms」。
  顺带把 LWW 的「同一毫秒两次写入算平局」也解决了（`nowIso()` 在同毫秒内是可能重复的）。
  已实现，见 `Repository.stampUpdatedAt`；测试在 `repository.test.ts` 的
  「同一毫秒里写两次，updatedAt 仍然严格递增」。
- **零新字段、零迁移**：`updatedAt` 本来就在实体上、本来就是服务端存的明文（§3.3）。
- AAD 的目的本来就是**防挪位置**（服务端改 `collection` / `id` / 换空间），这一点
  A 与 B 完全等价；而「同一 id 的旧密文顶新版本」在 A 下也挡得住——旧密文的
  `updatedAt` 更小，AAD 对不上，且 LWW 也会判它过期。

**方案 B（备选）：给十类实体补一个客户端 `rev` 字段**，写入时 +1，服务端原样存回。

- 保护强度与 A 基本一样，代价是**再动一次全部实体**（迁移 + 几十处测试夹具），
  而且 AAD 一旦上线就改不了（改了等于已存密文全部作废）。记录在这里是为了
  万一将来需要「同毫秒内也要分清版本」时有现成的备选。

服务端自己的游标仍然叫 `serverRev`，只活在同步层的 meta 里，**不进实体、不进 AAD**
（客户端把 `pull?since=` 的游标记在本地）。这一点与 §5 的「本地不该有服务端概念」一致。
§4.3 里那句「服务端决定新 rev」按此理解：**服务端决定的是 `serverRev`**，
记录自己的版本号由客户端用 `updatedAt` 表达。

### 4.5 第三步落地时补的四条细则（2026-09-19）

写同步循环时又遇到四处「协议没说死、但必须选一个」的地方，都按下面实现，
代码在 `packages/core/src/sync/`（`types.ts` / `merge.ts` / `loop.ts` / `memory-transport.ts`）：

| 细则 | 怎么定的 | 为什么 |
| --- | --- | --- |
| 消息排序 | **`createdAt` → `deviceId` → `localSeq`**（不是只看 `deviceId, localSeq`） | 只按设备分组排会让两台设备的消息各堆一头，读起来是断的；时间给的是人看着自然的交错，后两级保证同毫秒也有确定顺序。代价是设备时钟不准时顺序会歪——这是 §4.2 记下的已知代价 |
| 平局谁赢 | `updatedAt` 相同时**墓碑赢**，其余保留本地 | 「删掉」和「改了一下」撞在同一毫秒时，复活用户删过的东西比少一条更糟 |
| 回声推送 | 拉到的东西**不再推回去**（合并之后把推送点跟着推进） | 一台空设备首次同步会把整个世界拉下来；不更新推送点的话它会原样推一遍（无害但白跑流量）。自己推上去的记录会被拉回来一次（服务端不区分设备），合并判定「时间戳相同 → 保留本地」，一条都不改 |
| 场记游标 | 新增 `scene.recapUpToMessageId`，**优先按 message id**；老数据的 `recapUpToSeq` 继续兜底 | 合并之后一个场景里的消息来自两台设备，`localSeq` 会撞号（都从 1 开始），只按序号会漏摘一整段 |

还有一条**策略**决定：拉取时遇到解不开的记录（密码不对、服务端动过密文）→ **整轮停下报错，
游标不推进**，不静默跳过。理由：跳过等于把「有人动过你的数据」藏起来；停下至少有明确的
报错与可重试的状态。代价是「一条坏记录卡住整轮同步」——将来要加隔离机制时在这里改。

### 4.6 第四步补的两个接口：建空间与取空间元数据（2026-09-19）

§3.2 的草案只有 push / pull / head 三个接口。真去接线时发现少了两个——**第二台设备
必须能先拿到「包起来的主密钥」**，否则它连解密的钥匙都没有：

| 接口 | 谁用 | 要不要凭证 | 服务端存/给什么 |
| --- | --- | --- | --- |
| `POST /spaces` | 建空间的那台设备 | 不要 | 存 `spaceHandle`、两份凭证哈希、两份主密钥封装；已存在回 409（**不覆盖**） |
| `GET /spaces/{handle}` | 要加入的设备 | 不要 | 返回上面那四样（哈希与封装），**没有密码、没有明文** |

**为什么这两个是公开的**：加入的人还没有凭证（凭证要用主密钥算，主密钥要用封装解，
封装得先从服务端取），所以它们只能靠「知道句柄」来保护。这不算漏洞：封装是密文，
KEK 由用户密码派生，拿到也解不开；哈希是 SHA-256 的输出，反推不出凭证（凭证本身是
256 bit 的 HMAC 输出）。

**它的代价**写在明处：知道句柄的人能看出「这个空间存在、什么时候建的、有多少条记录」，
也能离线爆破密码（如果我们哪天把 KDF 参数调弱）。所以界面上仍要提示用户
「id 别填手机号」。

另外，这一步把服务端逻辑抽成了**一份**：`core/sync/server.ts`（纯逻辑 + 存储接口）
+ `core/sync/http.ts`（`handleSyncRequest`，fetch 风格）。三个宿主共用它们：

| 宿主 | 存储 | 状态 |
| --- | --- | --- |
| 内存服务端（`createMemorySyncTransport`） | Map | ✅ 单测 + 探针页在用 |
| 开发后端（`apps/web/tools/sync-dev-backend.ts`，挂在 vite 的 `/sync/*`） | JSON 文件（系统临时目录） | ✅ 真机验过（EVAL 第十节） |
| Cloudflare Worker（`deploy/cloudflare/`） | D1 | ⬜ 未做（下一步） |

**为什么现在就写下来**：这个空隙是写代码时必然会撞上的（实现推拉循环的第一天
就会解不开自己刚推上去的密文），而 AAD 定型后再改的成本远高于现在。

### 4.7 分页拉取的游标语义 ✅ 已定（2026-09-20，两处踩坑后的修正）

§4.3 的草案只说「`pull?since=rev` 拿记录、更新游标」，**没说这个 rev 是「这一批给到哪里」
还是「服务端现在到哪儿了」**。服务端一页只给 200 条（`DEFAULT_PULL_LIMIT`，上限 500），
两种理解在数据超过一页时会分道扬镳。真机上撞上的是后一种写法带来的后果：

**病**：服务端 `pull` 返回**全局头号**，客户端把它当新游标写进 meta。于是一台新设备
拉了一页就把游标推到末尾，剩下的记录**再也不会被请求**，而且下次同步还会说「两端一致」。
复现记录（两台浏览器 + 开发后端，2226 条记录的空间）：新设备拿到 **0 个世界、0 条消息**。

**定下来的语义（两处都改了，缺一不可）**：

| 位置 | 规则 |
| --- | --- |
| 服务端 `pull` 的 `head` | **这一批真正给到的那一条的 `serverRev`**；一条都没有时等于 `since`（不倒退、也不跳到全局头号）。全局头号另用 `serverHead` 返回，只给界面看「还差多少」 |
| 服务端 `pull` 的 `hasMore` | `head < serverHead`。客户端不必自己猜 |
| 客户端 | **一直拉到追平为止**：逐页解密、逐页合并（空间大时内存不必扛下整份），最多 200 页；只有整轮走完才推进游标 |
| 老服务端兼容 | 部署在用户服务器上的那版**不发** `serverHead` / `hasMore`，客户端退回「游标有没有追平它给的 `head`」来判断——所以**那台服务器不用改也能修好** |

**顺带定的第二件事：什么时候自动同步。** 原设计只有「启动时一次 + 手动一次」，
结果是「聊完一轮不动手就等于没同步」。现在每轮结算之后排一次，规则写在
`core/sync/auto-sync.ts`：两次自动同步之间至少隔 20 秒（一轮里会连着写好几次：
消息、记忆、情绪），窗口内的请求**合并**；被节流挡掉的那次会在窗口末尾**补一次**
（记忆通常比回复晚几秒才落库，不补这一趟就赶不上）；正在同步时又来请求只标记
「还要再来一趟」，不并发跑两个循环；**失败不重试**，只如实记进「上次结果」。

**为什么把这两件事写进协议文档**：第一条是**数据会不会丢**的问题（不是体验问题），
而它错在「协议没说清、两边各自理解」；第二条是**同步的触发时机**，属于协议的使用约定，
不写下来，下一个实现后端的人还会踩同样的坑。

### 4.8 坏记录隔离与分块推送 ✅ 已定（2026-09-21，顺序 13）

这两条都是「一台设备上出现过、但根子在协议用法」的问题。

**病一：一条坏记录卡死整台设备。** 原规则是「拉回来有解不开的记录就整轮抛错」，
当时的理由是「宁可让人看见，也不要少一条数据还装作同步成功」。真实后果是：
服务端上只要有一条损坏 / 被别的密码写过的记录，这台设备的游标就永远停在它前面，
**同步从此再也不动**，而且用户自己没有任何办法恢复。

定下来的规则：

| 位置 | 规则 |
| --- | --- |
| 客户端解密 | **逐条**试；解不开的那一条**跳过并隔离**，其余照常合并 |
| 游标 | 照常推进到这一页的最后一条（不然那条坏记录会永远挡住后面所有记录） |
| 上报 | 跳过的条数与明细（最多 20 条）进 `SyncReport.quarantined` / `quarantinedCount`，同步面板如实显示——**隔离不等于静默** |
| 停止条件 | 「服务端这一页没给东西」才停，不是「解开了几条」：一页全是坏记录时也要继续往下拉 |

**病二：一口气推一个几 MB 的请求。** 原来的 `push` 把「所有没推过的记录」装进一个请求。
一个用了半年、几千条消息的库第一次连同步时，那个请求会大到让手机流量先受不了
（服务端那时还没有限流）。

定下来的规则：**客户端按 200 条一块推**（`PUSH_BATCH_SIZE`，与拉取的默认页大小对齐），
块之间顺序发；哪一块失败，整轮失败、推送点不推进（下次从同一块重来，幂等）。
服务端另有 `maxRecordsPerPush`（默认 500）兜底。

### 4.9 服务端护栏：每空间配额与限流 ✅ 已定（2026-09-21，顺序 16）

邀请朋友之前必须有的那条线。数字都很宽松——正常用户一辈子碰不到，
但它们保证「出事时是有界的」：

| 限制 | 默认 | 超了怎么回 |
| --- | --- | --- |
| 一个空间最多多少条记录（含墓碑） | 50,000 | `413 space-full` + 一句人话（先导出封存再清理） |
| 一个空间最多多少字节（IV + 密文口径） | 256 MB | 同上 |
| 一次请求最多带多少条 | 500 | `413 space-full` |
| 一个空间每分钟最多几次写入 | 120 | `429 rate-limited` |

三条实现约定：

1. **护栏在核心里**（`createSyncServer` 的 `limits`），所以内存后端、开发后端、
   Worker 参考实现与用户自己的服务器**同一份规则**；自建服务器可以用
   `--max-records / --max-mb / --pushes-per-minute`（或对应的 `DRAMATIS_SYNC_*` 环境变量）调。
2. **限流状态放在进程内存**：它防的是「一次请求打爆」，不是精确计费；
   单进程部署下够用，不为它多写一张表。
3. **存储没实现 `spaceUsage` 就跳过配额检查**：不能让「加了个护栏」把旧后端变成起不来。

### 4.10 设备号上线上 + 两个新接口 ✅ 已定（2026-09-21，顺序 14 / 15 / 19）

这一条是**协议扩展**，不是实现细节，所以写在这里。

**改动本身很小**：`SyncWireRecord` 多了一个**可选**字段 `deviceId`（写这条记录的那台设备，
值是本机生成的随机 uuid，不含任何用户信息）。

| 为什么是可选 | 老客户端（这一版之前）不传它，服务端得照收；老服务端不返回它，客户端也得照跑 |
| --- | --- |
| 为什么放明文 | 服务端本来就要知道「谁在写」才能做设备列表与断开；它不是内容，泄露不了什么 |
| 服务端怎么存 | 记录行多一列 `device_id`。SQLite 用 `PRAGMA table_info` 探一次再 `ALTER TABLE`（幂等，老库自动补列） |

**两个新接口**（都要 `Authorization: Bearer`）：

| 接口 | 作用 | 说明 |
| --- | --- | --- |
| `GET /spaces/{handle}/devices` | 这个空间最近有哪些设备在写 | 返回 `{deviceId, records, lastWriteAt}`，按最后写入时间倒序 |
| `POST /spaces/{handle}/rotate` | **换同步密码** | 请求体 `{credentialHash, passwordWrap}`；服务端只替换密码那份哈希与封装，恢复码那份不动 |

**为什么「换密码」就是「断开一台设备」**：手上只有旧密码的设备，换完之后既过不了鉴权
（凭证哈希变了）、也解不开主密钥（封装换了）。它的本地数据还在，但**再也同步不了**——
这正是「旧手机丢了」时想要的那个效果，也是这三项里唯一会改变权限的动作。

**为什么换密码不重新生成主密钥**（顺序 15 的关键取舍）：换主密钥意味着所有记录都要
重新加密再上传，几千条记录全量重写，中途断网就是「一半新一半旧」。而主密钥本身没泄露——
它只活在设备的会话内存里，服务端拿到的从来只是封装。所以只换「锁」不换「里面的东西」。

**覆盖可见性**（顺序 19）顺带也靠它：合并时如果远端那条比本机旧、而且**写它的是另一台设备**，
就把「被哪台挡回去了」记进 `SyncReport.overridden` / `overriddenCount`，同步面板如实显示。
只统计别的设备——本机自己改两遍不叫覆盖。

**兼容性一句话**：老服务端上没有 `/devices` 与 `/rotate` 时，客户端回「这台服务端的版本
还不支持换密码」；设备列表则显示「还没记下任何设备」。**绝不假装成功**——
「以为换了密码、其实旧密码还能用」是这一项里最危险的谎。

## 五、这个选型要求数据层先补什么（P2-6 的第一步）

现状盘点（2026-09-19，**清单已全部交付**：三个提交 + 三条迁移，实现说明见
[ROADMAP.md](./ROADMAP.md) 的 P2-6，真机验证见 [EVAL.md](./EVAL.md) 第七节）：

| 要求 | 现状 | 要做的 |
| --- | --- | --- |
| 每个实体有 `id`（uuid） | ✅ `newId()` 就是 `crypto.randomUUID()` | 无 |
| 每个实体有 `updatedAt` | ⚠️ `Room`/`Conversation`/`Instance`/`Card`/`Persona` 有；**`Scene`/`Message`/`MemoryEvent`/`ChapterSummary` 没有** | 补齐，并在所有写入路径更新 |
| 软删除 `deletedAt` | ❌ 现在全是硬删（`repository.delete*` 直接 remove） | 加字段 + 改写删除路径 + 查询默认过滤 |
| 消息 `(deviceId, localSeq)` | ⚠️ 有房间级 `seq`，但没有设备标识 | 加本机 `deviceId`（存在 meta），消息带 `deviceId`，`seq` 改名 `localSeq` 并保持兼容 |
| 服务端 `rev` 游标 | ❌ | P2-6 时加在同步层，**不进本地实体**（本地不该有服务端概念） |

**建议顺序**：先补 `updatedAt` 与 `deletedAt`（纯本地改动、可测、不碰网络），
再做加密工具（`core/crypto`：派生、加解密、两种凭证），最后做同步循环与 Worker 参考实现。
每一步都能单独提交、单独测——这也是这个项目一直的节奏。
