# 服务器管理台设计（顺序 99：首批已实现，未部署）

> 目标：管理服务器上的同步空间、配额、设备与备份，**不读取角色卡、聊天、记忆、
> API Key 的明文**。用户已选 A（SSH 隧道＋本机网页）及“账户 ID／显示名＋关联空间”。首批只做账户资料认领和只读管理台，使用说明见 [sync-admin README](../tools/sync-admin/README.md)。

## 一、先纠正一个命名：服务器上没有“完整账号”

Dramatis 目前有两层：

| 层 | 存在哪里 | 里面有什么 |
| --- | --- | --- |
| 个人账户 | 用户设备 | 账户名、账户 ID、本地数据库、世界/角色卡/对话/记忆、模型配置、Key |
| 同步空间 | 服务器 | `spaceHandle`、凭证哈希、钥匙封装、每条记录的坐标与密文 |

原同步库不知道用户设备上的账户名。顺序 99 新增**自愿登记的运营资料**：用户登录／注册时明确同意，并用现有同步凭证证明空间所有权后，登记账户 ID 与显示名。`account_profiles` 只保存这两项、空间句柄、认领时间与空间世代；管理员不能代认领。旧空间／未同意者仍显示“未认领”，不能从句柄反推出账户 ID，也不能承诺列出所有设备本地账户。运营资料不属于加密实体正文，界面明确告知管理员可见；不建议用手机号／邮箱作为账户 ID。

## 二、服务端实际能看到什么

当前 SQLite 的核心结构是：

- `spaces`：`space_handle`、`created_at`、两份凭证哈希（`credential_hash`／`recovery_credential_hash`）、`key_wraps` JSON 与随机 `epoch`；两份钥匙封装装在同一个 JSON 列，不能读取或导出；
- `records`：`spaceHandle`、`collection`、`id`、`serverRev`、`updatedAt`、
  `deletedAt`、`sealed`、`deviceId`；
- 实际 SQLite 列名是 snake_case；另有 `heads`：`space_handle`、`head`、`record_count`、`byte_count`，是同步写入事务维护的计数器，不应遗漏；
- `account_profiles`：`space_handle`、`account_id`、`display_name`、`claimed_at`、`space_epoch`；只关联与 `spaces.epoch` 随机世代一致的资料；
- `sealed` 是 AES-256-GCM 密文；
- 日志只记方法、路径、状态与耗时，不记 `Authorization`，也不记请求体。

因此管理台能可靠展示的只有元数据：

- 空间数、已登记账户数、未认领数、账户 ID／显示名、空间创建时间；创建时间可能由客户端提供；
- `heads.record_count`（含墓碑）与 `byte_count`（配额计量，含行元数据）；旧库缺计数器显示未知；
- `SUM(length(CAST(sealed AS BLOB)))` 只取密文 JSON 长度，绝不取出 `sealed` 值；另有按集合的记录／墓碑计数和当前记录中的去重设备数；
- 客户端 `updated_at` 最大值不是服务器最近写入时间；`server_rev` 是顺序计数，不是时间。设备标识不是在线／安装设备数；
- 备份文件名、大小、修改时间与服务存活；不显示数据库绝对路径，不下载备份，不把“存在”当成“可恢复”；
- 配额配置尚为全局环境配置，限流窗口在进程内存；首批不展示伪造的按账户配额、限流用量或占用率。真正服务器写入时间、历史在线设备、单账户配额需后续新增持久化元数据。

管理台**不应该也不具备**的能力：

- 查看角色卡名称、开场白、世界书内容（顺序 90 起卡上已无「开场白」这个字段，这条边界照旧成立：卡的内容一概不给看）；
- 阅读对话、记忆、情绪、关系；
- 搜索消息或做内容审核；
- 查看 API Key；
- 用“重置密码”重新解密用户内容。

这不是权限做得不够，而是端到端加密协议的直接结果。任何“管理员可解密”的设计
都会把服务器变成新的信任中心，和当前产品承诺冲突。

## 三、威胁模型

未来的写管理面可以删除空间、改配额，所以被接管会损害可用性和完整性；首批仅 GET 白名单，不提供这些写入口，也不提供数据库导出。即便数据库是密文，仍含凭证哈希和钥匙封装，不应作为网页导出物。

主要风险：

1. **公网暴露**：扫描、弱口令、会话窃取、CSRF、XSS、依赖漏洞都会直接打到管理面；
2. **浏览器环境**：浏览器扩展、同机恶意页面、token 被脚本读取；
3. **误操作**：删错空间、把配额改到极小、用错备份覆盖生产库；
4. **内部越权**：未来如果有多个管理员，必须区分只读、可操作、可删除；
5. **日志泄漏**：管理操作日志不能顺手记录钥匙封装、凭证或密文。

软件端并不天然比网页端安全。真正决定安全边界的是：

- 服务是否只绑定回环地址；
- 是否必须经过 SSH / 系统登录；
- 管理凭证放在哪里；
- 是否有最小权限、审计与二次确认；
- 是否把管理接口暴露给公网。

## 四、三种形态的比较

| 方案 | 安全边界 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- | --- |
| A. SSH 隧道 + 本机网页管理台 | 服务只监听 `127.0.0.1`，先过服务器 SSH 登录 | 复用现有 Web 技术；公网没有管理端口；最容易先做对 | 每次要 SSH；手机操作不方便 | **第一版推荐** |
| B. Tauri 桌面管理端 | 凭证进系统凭据管理器；可做证书固定；无浏览器同源/Cookie 问题 | 体验最好；适合经常管理和多服务器 | 要维护桌面壳、签名、更新与安装；服务端仍需安全 API | 第二版推荐 |
| C. 公网网页管理台 | 单独域名 + 强认证 + IP 白名单 + 短会话 | 手机也能开 | 攻击面最大；认证与运维成本最高；最容易做错 | 仅在确有移动管理需求时做 |

**结论：先做 A。** 管理台本身可以是一套网页 UI，但不映射到公网，只放在服务器
回环地址；通过 SSH 端口转发访问。将来如果要桌面端，把同一套 UI 包进 Tauri，
不需要重写业务逻辑。桌面端的优势主要是“凭证放 OS 凭据管理器 + 无浏览器攻击面”，
不是“网页不安全的替代品”。

如果用户最终要求“手机随时管理”，才升级到 C，并至少配套：

- Passkey / WebAuthn；
- 单独的短时管理会话；
- 不在浏览器存长期管理 token；
- IP 或设备白名单；
- 严格 CSP、CSRF 防护；
- 所有删除与配额修改二次确认；
- 管理操作独立审计日志。

## 五、建议的第一版范围

### 首批已实现的只读面板

- 服务存活、备份文件元数据；无版本／库路径／恢复成功承诺；
- 账户与空间列表、搜索、分页：账户 ID、显示名、句柄、创建时间、含墓碑记录数、配额计量用量；
- 空间详情：按 collection 统计记录数；只显示 collection 名与计数，对 `sealed` 仅在 SQL 内聚合长度，不取出值；
- 空间详情另有密文 JSON 字节数、当前设备标识及计数、客户端更新时间；不将其叫“最近写入”。

### 后续独立顺序的受控操作（首批没有）

- 调整单个空间的配额；
- 备份只由服务器 CLI 生成和保管，不经管理网页导出；
- 需先补可信服务器写入时间，才能对长期无写入空间给出建议；
- 删除空间：必须输入完整 `spaceHandle`，并先自动做一次数据库备份；
- 重新加载配置或重启同步服务：第一版建议只给 CLI，不放进网页按钮。

### 明确不做

- 不展示或导出解密后的任何实体；
- 不提供“按用户 id 查看全部聊天”；
- 不提供“管理员重置用户同步密码后恢复内容”；
- 不把管理接口挂在现有 `/sync` 路径下；
- 不让 nginx 把管理端口反代到公网。

## 六、接口与认证草案

第一版建议新增一个独立的管理服务，不复用同步服务的公开端口：

```text
tools/sync-admin/
  src/main.ts       只监听 127.0.0.1:8788
  src/store.ts      只读元数据查询；首批无写操作
  src/audit.ts      追加式管理日志
  web/              本机管理 UI
```

访问方式：

```bash
ssh -N -T -J <旧机SSH别名> -p 22023 -L 127.0.0.1:8788:127.0.0.1:8788 <Windows用户>@127.0.0.1
# 然后在本机浏览器打开 http://127.0.0.1:8788
```

认证：

- SSH 是主认证边界；
- 管理服务仍要求一个随机 `DRAMATIS_ADMIN_TOKEN`，放在请求头；
- 正式拓扑是 Windows 服务＋现有管理 SSH 反向隧道（旧机回环 22023 → Windows 22），复用这条路径；每次运维：开隧道、打开回环网页、输入 token；
- token 用随机 32 字节生成，不写进仓库／URL／日志；Windows 环境文件用 NTFS ACL 限定服务身份与管理员可读（Linux 才用 `0600`）；
- token 只保存在页面内存，退出／刷新清除；严格回环 Host／Origin、CSP、no-store；
- 管理服务不设置公网 CORS；预检默认拒绝。

审计：

- 首批追加记录仅时间、固定动作标签、结果状态、耗时；不记目标、查询参数或账户资料。审计不可追加则查询失败关闭。未来多人／写操作需再设计操作者及目标审计；
- 不记录钥匙封装、凭证、`sealed` 或请求体；
- 审计日志本身只追加，不做网页删除入口。

## 七、建议的落地顺序

1. **管理文档与只读接口**：先把 SQLite 读模型和审计日志定下来；
2. **本机只读网页**：空间、用量、设备、备份，不提供任何写按钮；
3. **受控删除与配额**：加二次确认、自动备份与审计；
4. **桌面壳（可选）**：Tauri 包装同一套 UI，token 进系统凭据管理器；
5. **公网移动管理（暂不做）**：只有明确需要时才进入这一档。

## 八、需要用户拍板的方向

已选定并实施：

> **A：SSH 隧道 + 本机网页管理台，后续可按同一套数据层包成桌面端。**

如果用户需要“离开电脑也能在手机上管理”，则应明确接受 C 类公网管理面的风险，
而不是把 A 的管理端口直接暴露出去。

## 九、后续需求与分阶段验收／回滚

用户所说“分配内存”已明确为**服务器存储配额，例如每账户 1 GB**。不表示 RAM、模型上下文或本机磁盘。未来 VIP 可使用运营方提供的 API，且预留其它服务接口。

| 阶段 | 文件与验收 | 回滚 |
| --- | --- | --- |
| 顺序 99：资料认领＋只读 | `sync-server/src/accounts.ts`、客户端 `account-profile`／账户接线、独立 `sync-admin`；有效同步凭证才可认领、旧空间未认领、SQL 与响应不泄漏内容／凭证；只绑定回环、只有 GET；隔离 Windows 浏览器与五门禁见 EVAL 第九十一节 | 停管理服务／关闭转发；回退客户端和同步程序，资料表留存由旧版本忽略，不改同步记录 |
| 后续：存储配额＋受控写 | 新增持久化空间策略、同步事务中按空间 enforcing、管理确认／备份／审计模块；测试并发上传、降低至已有用量以下时保留数据但拒新增长、备份失败拒写、越权与误输入不写 | 停写管理入口；备份原策略并经审计恢复，不能把所有库直接覆盖 |
| 后续：VIP 与服务目录 | 新增权益表（生效／失效／撤销）、服务目录和独立网关；服务端校验权益／请求限额／费用预算；托管 Key 不给客户端，取消权益即时停止新调用；管理台仅服务配置与用量元数据 | 关闭对应服务能力，撤销权益；保留账目与审计，不影响加密同步 |
| 可选桌面壳 | `tools/admin-desktop/` 复用管理 API，系统凭据管理器存 token；签名、更新、隧道与凭据清除需独立验收 | 停桌面壳，继续 A 的网页与 SSH |

托管 AI 请求需要把用户选择的输入交给运营服务和模型提供方，与现有加密同步有不同隐私边界；未来必须明确告知并限制日志。本批没有托管调用、VIP 管理或其它服务实现。

具体风险防护：删除须完整句柄二次确认、先做带唯一时间戳的 `VACUUM INTO` 一致性备份、失败拒删；恢复先停写并保留当前库，在独立路径校验再人工切换，绝不直接备份覆盖在线 WAL 库；token 受 ACL 保护且不入 URL／存储／日志，泄漏后替换随机值、重启服务、退出全部旧页面。审计路径不得与库／WAL 重合，启动检查链接／硬链接。正式 Windows ACL／WinSW／管理隧道仍待部署授权后的真机验收；任务 73 的全面部署文档漂移仍开着。
