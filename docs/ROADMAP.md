# Dramatis 任务与发展路线图

> 本文档是**执行计划**，设计依据见 [DESIGN.md](./DESIGN.md)。任务编号在后续讨论与提交信息中复用。

## 一、方向判断

### 1.1 三个可能的方向

| 方向 | 说明 | 判断 |
| --- | --- | --- |
| A. SillyTavern 的替代品 | 正面做一个功能更全的酒馆 | **放弃**。生态、用户量、功能面都不是对手 |
| B. 给 ST 做记忆层 | 作为插件或伴生服务，被 ST 消费 | **放弃**。受 ST 形态限制，做不了多角色调度 |
| C. 多角色导演台 | 以「用户掌控阵容与记忆」为核心，兼容 ST 的资产格式 | **选择** |

选 C 的理由很简单：A 是拿自己的短处打别人的长处，B 是把自己的上限交给别人的架构决定。C 唯一的代价是要自己解决多角色与记忆，而这恰好也是本项目唯一值得做的事。

### 1.2 由方向推出的取舍原则

首批用户只会是 ST 的重度用户，而他们迁移的动机**只能**是「ST 做不到的事」。因此：

- 凡是「和 ST 一样、只是更好看」的功能，优先级一律下调
- 凡是 ST 结构上做不到的（阵容控制、视角化记忆、状态可干预），优先级上调
- 界面精致度不是差异化来源，**可干预性与记忆质量才是**

这条原则会直接决定后面的排序。举例：消息气泡更好看是 P3，而「查看并修改某个角色对某件事的记忆」是 P1——尽管前者的工作量可能更大、观感更明显。

### 1.3 四条硬约束

这四条是贯穿所有任务的约束，任何任务如果违反它们，方案就要重做。

1. **每个批次结束时都必须有一个能用的产品。** 不允许长期停在半成品状态。个人项目最大的风险不是做不完，而是做了三个月还是个跑不起来的东西。
2. **单回合额外调用 ≤ 2 次**（不含正式回复本身）。BYOK 用户自己付钱，成本是产品的一部分而不是实现细节。
3. **记忆必须可干预。** 用户能查看、修正、删除、置顶。角色说错话时，用户应该改记忆，而不是重开一局。
4. **`core` 保持零运行时依赖。** 这是各端复用与长期可维护性的前提，一旦引入平台依赖就会开始分叉。

### 1.4 优先级定义

| 级别 | 含义 | 判断标准 |
| --- | --- | --- |
| **P0** | 可用性门槛 | 不做就没有能日常使用的产品 |
| **P1** | 产品护城河 | 不做则与 SillyTavern 没有本质差别 |
| **P2** | 多端扩展 | 不做只影响便利性，不影响核心体验 |
| **P3** | 生态与打磨 | 提升留存与传播，可以长期慢慢做 |

### 1.6 平台范围

| 项 | 决定 |
| --- | --- |
| 必做平台 | Web（Windows 浏览器）+ Android |
| 多端关系 | 同账号，**共用同一条世界线** |
| Android 实现路径 | 优先 PWA（响应式 + 可安装）；只有 PWA 确实无法满足时才做 Capacitor 原生壳 |
| 桌面原生壳 | **暂不做，但保留可能**。触发条件见 P2-9 |
| iOS | 不考虑 |

**平台能力的获取阶梯**——优先用成本低的那一级，只有当前一级被证明不够用时才下降：

```
1. PWA           Windows 与安卓都能「安装」得到独立窗口，成本几乎为零
2. Tauri 桌面壳   当 PWA 出现解决不了的缺口时才做
3. Capacitor     同理，但构建链路比 Tauri 重得多，优先级更低
```

一个容易被忽略的事实：**Chrome / Edge 在 Windows 上支持 File System Access API**，所以 Windows 上的 PWA 已经能做带权限的文件读写，「导出到某个文件夹」这类需求不需要原生壳就能满足。

这个范围带来三个直接后果，它们会改变后面的优先级：

1. **同步从「便利功能」升级为「核心功能」。** 既然共用一条世界线，同步就是必需品而不是增强项。
2. **「本地优先」在移动端是脆弱的。** 移动浏览器会在存储压力下清理站点数据，Safari 的「7 天未访问即清理」是典型例子。所以本地优先必须配一张数据安全网：封存导出 + 尽早做云同步。
3. **后台任务不能假设能后台运行。** 用户关掉页面，抽取与状态更新就会中断。后台队列必须是幂等且可恢复的，下次打开时补做——这条约束直接写进了 P1-9。

**桌面壳暂缓的代价要说清楚**，这些缺口正是 P2-9 的触发条件：

- **标签页会被回收。** 桌面浏览器在内存紧张时同样会丢弃长时间不活跃的标签页，正在跑的后台任务一起中断，不只是手机的问题
- 失去 OS 级密钥存储（Windows 上是凭据管理器）
- 失去直接调用本地模型的能力
- 失去监控本地文件夹（自动导入导出的卡与备份）

**为了让桌面壳以后不贵，P0-1 会一次性定好平台能力适配层**（存储、密钥、文件读写、后台执行）。有了这层，将来加桌面壳是「写一个 adapter」，而不是「重构一遍」。

## 二、P0：可用性门槛

**目标**：把「刷新就没了」的演示品，变成能存住东西、能多人同场、能日常聊的工具。

**为什么持久化排在多角色之前**：现在没有任何持久化，刷新页面一切归零。它既是最低成本的改动，也是后面所有功能（记忆、同步、导出）的地基。先修地基不会浪费。

### P0-1 本地存储与平台能力适配层 · L

- 实体表：`room` / `scene` / `message` / `card` / `instance` / `worldbook` / `settings` / `memory`
- 版本化迁移机制（schema version + 迁移脚本），从第一天就留好升级路径
- **平台能力适配层**——四组接口，这是让桌面壳选项以后不贵的关键（见 §1.6）：
  - `Storage`：Web 用 IndexedDB（见下方实现说明），将来桌面壳换成本地 SQLite
  - `KeyStore`：当前提供「仅会话」与「明文落盘」两档，口令加密属于 P2-8；桌面壳换成 OS 凭据管理器
  - `FileIO`：Web 用 File System Access API，并以下载 / 上传作为回退
  - `BackgroundRunner`：Web 用可恢复的工作队列，将来桌面壳换成常驻进程
- P0 / P1 阶段这四组只需要 Web 实现，但**接口必须先定下来**，否则后面加端就是重构而不是加壳
- 所有写操作走统一的仓储接口，避免 UI 直接碰存储
- **验收**：刷新浏览器、重启应用后，房间、场景、消息、角色实例完整恢复；把任一 adapter 换成测试假实现后，`core` 的测试仍然全绿
- **依赖**：无

**实现说明（2026-09-16 交付）**：原先计划 Web 端用 SQLite WASM + OPFS，实际改用 IndexedDB。理由是 SQLite WASM 会引入 WASM 产物与 Worker，而 Node 环境下无法在单测里覆盖；IndexedDB 不增加任何运行时依赖，且过滤与排序直接复用 `core` 的实现，因此跑在内存实现上的 86 个测试对浏览器实现同样有效。适配层正是为了这种替换而存在——若将来 IndexedDB 成为瓶颈，换回 SQLite 只动一个文件。

另外补入两项计划外但必要的内容：消息的 `seq` 字段（房间内单调递增，不依赖时间戳排序，为 P2-6 的跨设备合并铺路），以及 `KeyStore` 与实体表的分离（实体只存 `keyRef`，密钥永不进入可同步的数据）。

### P0-2 会话恢复与自动保存 · M

- 启动时恢复到上次的房间与场景，而不是空白页
- 消息、场景设置、角色状态在变更后立即落盘
- 崩溃或意外关闭后不丢数据
- **验收**：对话中途强制关闭页面，重新打开后内容不丢
- **依赖**：P0-1

### P0-3 多角色实例管理 · L

- 一个房间里可以容纳多个角色实例，每个实例独立持有 presence、情绪、关系、记忆
- 从同一张角色卡派生多个实例（例如「同一个角色的不同时间线」）
- 实例级别的覆写：显示名、称呼、对玩家的初始关系
- 玩家 persona 支持多个身份并可在房间内切换
- **验收**：一个房间内三名角色同时存在，各自状态互不干扰
- **依赖**：P0-1

### P0-4 发言调度 v1（规则版） · M

- 按设计文档 §3.1 的信号做规则判定，**不调用额外模型**
- 信号：是否点名、关键词命中、冷却惩罚、公平性补偿、外向权重、presence 过滤
- 输出有序发言者列表，允许长度为 0
- 提供调试视图：显示每个角色的得分与落选原因
- **验收**：三角色同场时不会出现抢话或全员沉默；能说清「为什么是他接话」
- **依赖**：P0-3

### P0-5 每角色独立的近期上下文切片 · M

- 工作记忆层（设计文档 §4.1 第一行）的独立化：每个角色看到的历史是**自己的视角**
- 只包含该角色在场时发生的消息，以及他参与过的回合
- **零额外模型调用**，纯粹是历史裁剪
- 这是 P1 完整记忆系统的地基，也是「角色有各自视角」这个感受的最低成本来源
- **验收**：角色离场期间发生的对话不会出现在他的上下文里
- **依赖**：P0-3

**实现说明**：这条规则落在了消息的 `audience` 字段上，而不是靠 prompt 里写一句「你不记得之前的事」。消息在落盘时记录当时在场的角色实例，裁剪时只保留参与者可见的部分。于是「角色不知道他不在场时发生的事」变成结构上的必然，而不是祈求模型配合。

这个字段还有第二个用途：P1-2 的记忆抽取需要知道该给谁写记忆，而只有当时的在场者才该拥有那段记忆。现在把它定下来，P1 就不需要再改数据模型。

### P0-6 场景控制面板完整化 · M

- 在场名单的可视化管理：拉人入场、驱逐、切换 presence（onstage / muted / offscreen / absent）
- 入场策略四种模式的完整 UI 与后端行为（锁场禁用一切自动入场）
- 场景切换：结束当前场景、开启新场景、保留历史场景
- **验收**：能在三步之内完成「把 A 请出场、锁场、只留下 B」这套操作
- **依赖**：P0-3

### P0-7 重抽与消息编辑 · M

- 重抽（swipe / regenerate）、编辑、删除，是这个品类使用频率最高的交互，没有它产品会显得残缺
- **关键设计约束**：记忆写入必须能回滚。重抽意味着上一版的抽取结果要作废，否则角色会同时记得两个互相矛盾的版本
- 为此 P1 的记忆写入必须按回合分组，支持按 turnId 撤销
- **验收**：连续重抽五次，角色的记忆里只留下最终采纳的那一版
- **依赖**：P0-2

**实现说明**：当前只允许重抽**最后一条**角色回复。重抽更早的消息会让后续对话失去前提，正确做法是连带截断后面的内容，那属于 P3-6 的消息分支。UI 只在最后一条回复上显示重抽按钮，避免给出做不到的承诺。

撤销路径已经打通：重抽时先调用 `queue.cancelByTurn(turnId)` 取消该回合排队中的记忆抽取，再删除旧回复，然后用同一个 turnId 重新生成。P1 接入真实抽取时，这条链路不需要改动。

### P0-8 多服务商配置管理 · S

- 保存多套配置（地址 / Key / 模型 / 参数），可在房间间切换
- 为 P1-9 的「后台任务用便宜模型」预留独立配置位
- **验收**：能在两套配置之间切换并立即生效
- **依赖**：P0-1

### P0-9 工程基线：CI + Lint + Format · S

- CI 跑 typecheck + test，防止后续大改时静默退化
- 统一的 lint 与格式化规则
- 成本极低，放在最前面是为了保护后面所有工作
- **验收**：PR 与 push 都会触发检查
- **依赖**：无

### P0 完成后的状态

一个可以在浏览器里长期使用的多角色扮演工具：多个角色同时在场、各自有独立视角、可以随时拉人驱逐锁场，数据不会丢。

**但它还不记得任何超过上下文窗口的事**——这正是 P1 要解决的。

## 三、P1：护城河

**目标**：让角色真正记住，并且让用户能看见和修正。

**为什么记忆内部也要排序**：最大的未知不是「能不能存」，而是「抽出来的记忆是否真的让对话更好」。所以前四项（抽取 → 存储 → 召回 → 干预）构成一个**最粗糙的完整闭环**，先拿真实对话验证效果，再谈分层摘要和向量检索。反过来先建好向量库和三层摘要再去验证，是本项目最容易踩的坑——那会把三周花在一个还没被证明有价值的系统上。

### P1-1 记忆抽取最小闭环 · L

- 每回合结束后异步抽取一条事件，结构化字段见设计文档 §4.3
- 先用单条主观条目起步，不做分段与多视角
- 抽取必须异步，不阻塞回复
- **验收**：聊二十回合后，数据库里能看到二十条有意义的记忆
- **依赖**：P0-5

### P1-2 视角化存储 · M

- 为每个在场角色生成以他视角为准的条目：他注意到了什么、误解了什么、在意什么
- 同一事件在不同角色的记忆里允许互相矛盾——这是特性，不是 bug
- **验收**：三个角色被问起同一件事，回答有合理差异且各自自洽
- **依赖**：P1-1

**实现说明（P1-7，2026-09-16）**：推演与记忆抽取并列挂在同一个后台队列上，**一次调用推演出所有在场角色的变化**，不是每人一次。幂等靠「该回合已经推演过就跳过」判断——否则重试会让关系翻倍。每条变化都必须带理由，界面上能展开看最近三次。v1 的关系变化只算在玩家头上，角色之间的关系边留给后续。

**实现说明（P1-8，2026-09-16）**：三道闸都在 `memory/affect.ts` 里——单轮变化上限 0.3、每轮情绪向中性褪色 8%、所有值域夹紧。写测试时发现一个真问题：**褪色最初没有写进历史，导致重抽无法还原**，反复重抽会让情绪单向漂移。现在褪色也作为一次变化记录，撤销变成精确的（除夹紧边界外）。

需要说清的一点：**特质轴（慢变量）目前是静态的**，直接来自角色卡，不参与漂移。会漂移的是情绪与关系，抗漂移也针对它们。所谓「性格漂移」在这个模型里表现为情绪与关系的累积偏移，而不是特质轴本身变化。

### P1-3 混合召回 v1 · L

- 评分 = 关键词 + 重要度 + 时效 + 关联过滤（在场者 / 地点 / 时间线）
- **先不做向量**，把确定性部分调准
- 每个角色有独立的记忆预算，按分数裁剪
- **验收**：提到很久以前出现过的人名，角色能想起相关的事
- **依赖**：P1-2

### P1-4 记忆面板与人工干预 · L

- 时间线视图，按角色筛选
- 查看某条记忆的原始出处（点回当时的对话）
- 编辑、删除、置顶、调整重要度
- 这是本项目相对 ST 最直观的差异化能力，也决定用户对系统的信任程度
- **验收**：发现角色记错时，能在 30 秒内定位并修正
- **依赖**：P1-3

**批次 3 实现说明（2026-09-16 交付）**：

- **抽取走后台队列，负载只存 id**：任务里带的是「房间 / 场景 / 回合」三个标识，消息内容在任务执行时现取。这样重试与跨会话恢复都不会因为负载过期而出错，也不会把同一条消息存在两个地方。写入前先按 `sourceTurnIds` 清掉该回合的旧记忆，所以重试天然幂等。
- **一次调用产出全部视角**：抽取的返回里既有客观经过，也有每个在场角色的一条主观印象。不是每个角色各调一次模型——这是把额外调用压在每回合一次以内的关键。
- **客观条目与视角条目分开存**：客观条目（`observerId` 为 null）给用户看，用来对比「实际发生了什么」与「每个人记得什么」；视角条目才是角色召回时使用的。抽取**不做一致性校验**，同一事件在不同角色记忆里允许矛盾——强行对齐就正好毁掉了这个特性。
- **中文用二元组近似分词**：`酒馆老板` 切成 `酒馆 / 馆老 / 老板`，不引入分词库，行为完全可预测。召回权重是加法且可解释，和调度器一样能说清「为什么想起这件事」。**刻意不做向量检索**，等 P1-10 的评测证明关键词不够用再说。
- **每角色记忆预算 800 token**，超出按分数裁剪；被回想过的记忆累计 `recallCount` 并参与后续评分，形成「越想越牢」。
- **手动改过的不会被动**：用户调整重要度时打上 `importanceLocked`，之后的衰减与重锚都不覆盖；置顶的条目不参与衰减。

### P1-5 分层摘要与压缩流水线 · L ✅ 已完成（T3，2026-09-19；遗忘机制另半留下）

- 轮 → 场景 → 章节三层摘要；触发条件为轮数阈值或上下文占用超阈值
- 被压出窗口的原文**永不删除**，随时可展开回想
- 遗忘机制：低重要度且长期未被回想的记忆降权，可合并为粗粒度印象
- **依赖**：P1-1

**实现说明**：

1. **两层自动摘要**：`scene.recap`（攒够 8 轮或 2400 token 压一次，游标
   `recapUpToSeq` 保证同一段话不会被压两遍）与 `chapterSummaries` 集合
   （攒够 3 场有场记的戏滚成一段）。触发与解析都是纯函数，可测可解释。
2. **原文永不删除**：摘要只读原文，只是让「已经过去的部分」在 prompt 里有个便宜的载体。
3. **场记与场景设定分开存**：`scene.summary` 是人写的简介（角色卡 scenario，用户可改），
   `scene.recap` 是自动整理的经历。混在一个字段里会互相覆盖。
4. **判断只做一处**：界面在每轮结算后只负责「来看一眼」，攒够没攒够由后台任务拿着最新
   数据决定。真机第一轮出现过两次摘要调用——界面侧的判断用的是渲染时的旧场景对象。
5. **仍未做**：DESIGN §4.5 的「低重要度记忆合并成粗粒度印象」。召回侧的时效衰减
   早在 P1-3 就有了，合并没有。

### P1-6 发言调度 v2：意图先行 · L ✅ 已完成（T2c，2026-09-19）

- 生成对白前先产出「此刻想做什么」的意图
- 调度判定改用便宜模型与规则的混合，正式生成才用主模型
- 支持插话、抢话、欲言又止、主动发起
- **依赖**：P0-4

**实现说明（与原始计划的偏差）**：

1. **不让模型自己写意图行。** 一开始试的是零成本方案——要求模型在回复开头写一行
   `意图：…`，我们解析出来单独存。真机 4 回合 **0 次遵守**，和 `#` 是同一类元指令问题
   （见 [EVAL.md](./EVAL.md) 第五节）。所以改成**生成前真的多问一次**，
   用便宜模型（后台模型配置）判断谁开口、想做什么。
2. **预算从批量合并里出。** 原来后台固定两次调用（记忆抽取 + 情绪推演），两者吃的是
   同一批消息、同一批在场角色，合并成一次 `turn.analyze`
   （`memory/turn-analysis.ts`）。账变成「1 生成 + 1 意图 + 1 合并后台」，
   **每回合额外调用仍是 2 次**，P1-9 的批量合并顺带落地。
3. **意图是建议不是命令。** 名字对不上在场角色、`presence` 不是 `onstage`、
   `hold_back`——任何一条都丢弃并退回规则调度；调用或解析失败一律静默退回，
   这一轮照样能玩（`director/intent-plan.ts`）。
4. **做成开关。** 会话模式里加了「意图先行」（缺省开）：BYOK 用户想省一次调用可以关掉，
   退回纯规则调度。见 [LAYOUT.md](./LAYOUT.md) 取舍第 10 条。
5. **验收证据**：EVAL.md 第六轮——三轮真机上角色都照着自己的打算落笔
   （反问、不得不表态、顶回去），合并后的状态变化照常写入。

### P1-9 调用预算与后台任务调度 · M ✅ 已完成（T2c 批量合并 + T19 熔断，2026-09-19）

- 统一的后台任务队列：抽取、状态更新、摘要、重锚都在这里排队
- 后台任务可使用独立的（更便宜的）模型配置
- 批量合并：能攒的攒起来一次做完，不能攒的才实时
- 调用计数与熔断：超出上限时降级为规则版，而不是报错

**实现说明**：

1. **批量合并**（随 T2c 落地）：记忆抽取与情绪推演吃的是同一批消息、同一批在场角色，
   合并成一次 `turn.analyze`；省下的那一格给生成前的意图调用，总额仍是
   「每回合额外调用 ≤ 2」。
2. **熔断**（T19）：上限挂在世界上（`room.budget`），两个口径——**额外调用次数**
   （不依赖单价，谁都能用）与**花费金额**（要先在模型接入里填单价）。
3. **只停生成之外的调用**：意图判断、一轮分析、分层摘要会被跳过，**角色回复照常生成**
   ——聊到一半突然说不出话，比多花几分钱糟糕得多。用户主动发起的调用
   （生成、副对话）不受限：上限管的是「我没让它花的钱」。
4. **判定只用最新数据**：每一趟后台任务开始前重算一次账单，而不是信界面渲染时的状态
   （队列会积压、界面会滞后）；队列里剩下的任务直接收掉，免得每次启动重跑。
5. **验收证据**：EVAL 第四节——上限设成 2（当时已用 9 次）后发一轮：回复照常生成，
   意图与后台全跳过，账单只多一次「角色生成」。
- **队列必须幂等且可恢复**：移动端浏览器不保证后台运行，用户关掉页面任务就中断，下次启动要能补做且不产生重复记忆。这条约束来自 §1.6
- 重抽撤销（P0-7）与队列补做必须能共存：撤销一个尚未执行的任务，等同于取消它
- **验收**：正常回合的额外调用 ≤ 2 次；成本可被用户预估
- **依赖**：P1-6

**实现说明（2026-09-16，部分交付）**：

已交付：抽取与推演共用一个后台队列（不再各起一套定时器）；后台任务可用独立模型配置，面板上已补 UI；队列幂等且可恢复，启动时把中断的任务捡回来；重抽与删除消息会连带撤销队列任务与已写入的状态；会话内的后台调用次数直接显示在记忆面板上。

## 四、P2：多端（同账号，共用一条世界线）

**目标**：让这条世界线在 Windows 浏览器与安卓之间自由流动。

**平台范围**（见 §1.6）：Web（Windows）+ Android，同账号共用一条世界线。两端都优先走 PWA；桌面壳保留可能但暂缓（P2-9），Capacitor 只在 PWA 确实不够用时才做（P2-10）；不考虑 iOS。

**为什么顺序是「先能上手机，再谈同步」**：在安卓上跑起来是同步的前提，而 PWA 化本身成本不高。但数据安全必须紧跟其后——移动端浏览器随时可能清掉本地数据，在同步做出来之前，**封存导出是唯一的兜底**。顺序颠倒过来会让人在没网盘保护的情况下开始用手机聊。

- 断点布局：窄屏时侧栏折叠为抽屉，对话区占满
- 触屏交互：安全区适配、软键盘顶起、点击区域放大、返回键行为
- 长对话下的渲染与滚动性能
- **验收**：在安卓 Chrome 上单手完成「导入卡 → 开聊 → 切场景」全流程
- **依赖**：P0-1

### P2-2 PWA 化：可安装与离线外壳 · M

- Web App Manifest：图标、主题色、standalone 显示模式
- Service Worker：应用外壳离线可用
- **模型请求一律不缓存**——那是用户的钱和数据，只缓存静态资源
- **验收**：在安卓上「添加到主屏幕」后，断网也能打开并看到已有对话
- **依赖**：P2-1

### P2-3 本地存储的持久化与配额管理 · M

- 调用 `navigator.storage.persist()` 申请持久化存储，并检测是否获批

- **依赖**：P2-1

### P2-8 API Key 的存储策略 · M

- **浏览器拿不到 OS 级安全存储**：Windows 与安卓的浏览器都不提供凭据管理器的访问入口，而桌面壳暂未做（见 P2-9）
- 可选方案：仅会话内保存（最安全、最麻烦）、口令加密后落盘（WebCrypto 派生密钥）、依赖浏览器自身存储（最方便、最弱）
- 建议默认「口令加密落盘」，并允许用户选择「不保存」
- 若日后启用桌面壳，本项升级为 OS 凭据存储，口令加密退居为同步加密的密钥派生手段
- **依赖**：P2-5

### P2-9 Tauri 桌面壳（条件性） · L

- **触发条件**：出现 PWA 解决不了的具体缺口，按现实可能性排序——
  1. 标签页被回收导致后台任务中断（桌面浏览器同样会发生）
  2. 需要 OS 级密钥存储
  3. 需要直接调用本地模型
  4. 需要监控本地文件夹做自动导入导出
- **为什么排在同为条件性的 Capacitor 之前**：Tauri 复用同一套 React UI，构建链路只多一个 Rust 工具链；安卓要 Android SDK、Gradle、签名与分发，重得多。真要做的话，桌面壳更可能被做出来
- Windows 上 WebView2 是系统自带组件，不需要额外分发
- 启用后 P2-8 可升级为 OS 凭据存储
- **依赖**：P0-1（适配层）、P2-3

### P2-10 Capacitor Android 壳（条件性） · L

- **触发条件**：PWA 在安卓上确实无法满足时才做。典型缺口是可靠的后台任务与系统通知

### P3-7 用量与成本统计 · M ✅ 已完成（T7，2026-09-19）

按回合、按角色、按后台任务统计 token 与费用。BYOK 用户需要这个才能做判断。

**实现说明**：

1. **单开一份只增不改的流水**（`storage/usage.ts`，集合 `usageRecords`），而不是把用量
   挂在任务或消息上——任务记录会被 `clearTurn` 清掉（重抽、改归属），消息会被用户删除，
   而钱已经花了。第一版是会话级计数，五十回合长跑中途重载两次就把全程账单冲掉了。
2. **服务商不返回 usage 也记一笔**（token 记 0）：漏账比零账更糟，会让人低估开销。
3. **单价由用户填**（每百万 token 的输入 / 输出价 + 币种），不内置价格表——模型改名、
   降价、不同地区价格都不一样。没填就只报 token，**不编价格算钱**；只覆盖一部分时
   界面上显式标出「N/M 次有单价」。
4. **归档不回滚账单**：归档的语义是「这条时间线没有发生过」，但那次调用真的计费了；
   只有整个世界被删掉时才由仓储层清账。
5. 界面上是运行时面板新增的「用量」页（世界 / 本对话两级总计 + 三张分组账）。

**未做**：按回合倒排的花费明细（单条消息上的用量已经在气泡里）；
**顺带解锁**：P1-9 的预算熔断从此有了真实成本数据。

### 批次 7 · 界面改版（按 LAYOUT.md 的三批）

这一批不在原来的 P0–P3 编号里，它来自手绘草图与逐区域填写，规格见
[LAYOUT.md](./LAYOUT.md)。之所以插在批次 4 中间：P1-10 的真实模型验证需要
一个能承载完整创作流程的界面，而改版前「世界」与「对话」是同一层，
用户连第二条线都开不出来。

| 序 | 任务 | 说明 |
| --- | --- | --- |
| 28 | A 布局骨架 | 顶栏只留折叠、左栏三段、主区标题栏、`#` 动作分段、输入区按钮与对话模式、右栏角色栏 |
| 29 | B 世界 → 多对话 | `Conversation` 实体、schema v3 迁移、归档（状态快照 + 按对话撤销记忆） |
| 30 | C 副对话与工具 | 世界管理员、三个工具（角色卡 / 世界书 / 场景）、工具调用循环、草稿采纳 |

**实现说明（2026-09-16 交付）**：

- **对话是一等实体**，不是房间上的一个字段。Room 从此只表示「世界」：角色、
  角色卡、世界书、玩家身份是世界级的；场景、消息、对话模式是对话级的。
  迁移 v3 给每个旧世界补一条「主线」，并把旧场景、消息与记忆认领过去。
- **归档是可逆操作的反面**：它把情绪与关系还原到这条对话开始时的快照，
  并按 `conversationId` 删掉这条线产生的记忆；对话本体、场景与消息都保留，
  移出主列表，改从设置里只读打开。快照在**创建对话时**就写好——事后再补
  是补不出来的。
- **副对话的工具是真调用**：模型请求 → 内核校验参数 → 界面执行 → 结果回填
  → 模型接着说。校验失败不抛异常，而是把「cardId 不存在」这类话作为工具结果
  回填，让模型自己改；三轮封顶，最后一轮强制用文字收口。
- **草稿由用户决定去留**：角色卡与世界书在采纳前只挂在消息的 `artifacts` 上，
  场景类工具即时生效（否则用户看不到任何变化）。
- **刻意没做**：顶栏的世界视图蓝图（节点网络）继续留空；归档没有「取消归档」；
  角色拖入不写旁白（规格只要求切换场景写）。这些都记在 LAYOUT.md 的取舍里。

## 八、验收标准

对一个个人项目来说，模糊的「感觉不错」是没法判断进度的。以下是可检验的信号：

| 能力 | 验收信号 |
| --- | --- |
| 长线不崩 | 50 回合内不出现设定自相矛盾 |
| 多角色不串味 | 三角色同场时，各自记得的事有明显差异且各自自洽 |
| 成本可控 | 单回合额外调用 ≤ 2；用户能预估一局的费用 |
| 数据可靠 | 刷新、重启、换设备都不丢数据 |
| 可干预 | 30 秒内能定位并修正一条错误记忆 |
| 角色不趋同 | 50 回合后仍能靠说话方式区分角色 |

## 九、明确不做的事

写下来是为了以后能理直气壮地拒绝。

- **不做模型代理服务。** 流量由客户端直连服务商，后端不碰 Key 与明文
- **不做角色卡市场或社区分发平台。** 至少 P3 之前不考虑
- **不追 STscript / 快速回复的完整兼容。** 那是另一个完整的脚本生态
- **不执行角色卡内的任意 JS。** 安全边界，见 P3-5
- **不做托管算力。** 与 BYOK 定位冲突
- **不为了对齐 ST 的界面而重做 UI。** 界面不是差异化来源
- **暂不做桌面原生壳。** 保留可能，触发条件见 P2-9，在此之前不投入
- **不用 Electron。** 若日后做桌面壳，选 Tauri
- **不考虑 iOS。** 平台数量是个人项目的维护上限
