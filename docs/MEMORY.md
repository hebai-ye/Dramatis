# 记忆与长对话：现状、测量与方案

> 这份文档回答四个问题：① 500 条消息会不会出问题；② 什么时候提炼 / 压缩；
> ③ 新对话该带多少记忆、怎么带才不臃肿；④ 记忆怎么影响性格与情感、怎么回滚。
> 所有数字都来自本机实测（假模型、可复现），测量方法在最后一节。

## 一、结论先摆出来

| 问题 | 现状 | 该做什么 |
| --- | --- | --- |
| 500 条消息会不会「炸」 | **不会**。提示词从第 60 轮起封顶在 **3,754 字**（装配只带最近 40 条历史 + 记忆预算），300 轮实测 0 报错 | 不用为「上下文超长」改造装配 |
| 真正的问题是什么 | **记忆池线性膨胀**：300 轮 → **590 条记忆**（约 2 条/轮）。每次召回想带也带不了几条，于是「越聊越记不住真正相关的那条」 | 记忆**合并 + 索引化**（顺序 27），这是本主题的核心 |
| token | 300 轮合计 ≈ **170 万字输入 / 11 万字输出** ≈ **93 万 token ≈ 2.2 元**；平均每轮约 2,600 输入 + 190 输出 | 带记忆进新对话必须**按索引**，不能按全文 |

## 二、实测曲线（300 轮 / 601 条消息）

```
第 25 轮   消息  50 条   记忆  44 条
第 50 轮   消息 100 条   记忆  92 条
第 100 轮  消息 201 条   记忆 196 条
第 200 轮  消息 400 条   记忆 394 条
第 250 轮  消息 501 条   记忆 492 条
第 300 轮  消息 601 条   记忆 590 条      ← 页面上的错误块 0 个，页面级错误 0 条
```

**记忆 ≈ 2 × 轮数**（每轮一条客观经过 + 每个在场角色一条视角）。这既是这个产品的特色
（每个角色记的东西不一样），也是它的负担。

提示词长度（`generate` 调用）：

```
第  1 次 1001 字 → 第 31 次 1604 字 → 第 61 次 3733 字 → 之后一直在 3754 字上下浮动
```

**为什么封顶**：`assemble.ts` 只带**最近 40 条**历史（`historyLimit ?? 40`）+ 记忆召回按预算
挑几条。所以上下文不会无限涨——这是**好**的；代价是「40 条以前的事」只能靠记忆与章节回顾，
而它们现在有 590 条、没有层级。

## 三、什么时候提炼与压缩（问题②）

现在已有的三层（都在跑，各有节奏）：

| 层 | 何时跑 | 产出 | 实测频率（300 轮） |
| --- | --- | --- | --- |
| 一轮分析 | **每轮** | 客观经过 + 各角色视角（1 + N 条） | 322 次 |
| 分层摘要 | 每若干轮 | 「这一场到目前为止发生了什么」 | 42 次（约每 7 轮） |
| 章节回顾 | 场景结束时 | 一章一句话 | — |

要补的是**第四层：记忆合并（粗粒度印象）**。建议的触发线（第一版，之后按数据调）：

| 触发条件 | 做什么 | 为什么是这条线 |
| --- | --- | --- |
| 一条对话里**同一视角**的低重要度记忆（`importance ≤ 0.5`）超过 **20 条** | 把它们合并成 **1–3 条「印象」**（例：「这半个月他一直在替秦娘挡账房的事」） | 300 轮 590 条里绝大多数是这类「日常经过」，它们挤占召回预算却几乎不会被单独需要 |
| 一条对话超过 **120 条**记忆 | 全量跑一次合并，并按 20 轮一段生成时间线索引 | 120 条是「召回预算（几条）× 轮数」之间开始失真的位置 |
| 每 **40 轮**（或每 300 条消息） | 生成一条**阶段性印象**，同时刷新索引 | 与已有的分层摘要同频，避免另开一套节奏 |

> **上面这两个数字是按演练调过的**：一开始写的是「≤0.4 / 40 条」，50 轮演练里
> **一条都没合并**——抽取出来的日常经过普遍在 0.45 上下，而门槛只算低重要度的那些，
> 单角色对话里一个视角每轮才产出一条。于是定成 **≤0.5 / 20 条**：
> 20 条压成一条印象已经足够有用，也让「池子不再线性涨」更早发生。

**硬约束（三条，写在这里是因为它们决定实现对不对）**：

1. **合并只标「已被取代」，绝不删原文**。原文留在库里、仍能被面板搜到，
   合并出来的印象通过 `supersedes: EventId[]` 指回去——这是回滚与「这件事我记错了」的唯一依据。
2. **合并要按视角分开**：A 眼里的印象与 B 眼里的印象本来就是两件事，混起来会让角色失去差异。
3. **合并本身是一次模型调用**，所以要能省就省：只对低重要度、同一视角、时间相邻的记忆做，
   并且**在后台队列里跑**（用便宜模型），不能阻塞对话。

## 四、新对话带什么、带多少（问题③）

你的构想（**附件像文件夹、按关键词检索**）与这里的结论一致：**常驻的永远是索引，正文按需取**。

新对话开始时，把原对话的东西压成**三层**塞进角色卡附件：

| 层 | 内容 | 大小预算（第一版） |
| --- | --- | --- |
| ① 关系现状 | 一句话：这个角色此刻怎么看待玩家（由情感/关系状态生成） | ≤ 60 字 |
| ② 时间线索引 | 每章一行（章标题 + 一句话）+ 关键词 | ≤ 20 行 ≤ 600 字 |
| ③ 记忆索引 | 每条印象一行：**关键词 + 半句话**（不展开正文） | ≤ 60 行 ≤ 1,000 字 |
| 合计常驻 | | **≈ 1,600 字 ≈ 800 token** |

**为什么不臃肿**（用实测数字算）：590 条记忆全文 ≈ 4.7 万字 ≈ 2.4 万 token，不可能全带；
合并成 ~50 条印象后全文 ≈ 8,000 字（4,000 token）也还是贵。**索引化**之后 1,600 字封顶，
而命中的那几条正文（每次 2–3 条，≤ 400 字）在**对话里出现关键词时**才注入。

**「什么时候去搜」**（这正是你提的那条，也是最省 token 的一环）：

1. **关键词命中**：用户这句话里有索引里的关键词（「秦娘」「货栈」「那批货」），
   就把对应的 2–3 条正文注入本轮提示词；
2. **意图命中**：用户在问过去（「还记得吗」「上次」「以前」），同样触发检索；
3. **不触发就一点都不带**：日常闲聊只带 ①（关系现状）那一句——
   **这是省 token 的关键**，也是「记忆像文件夹」这个比喻真正的落地方式。

> 这一条与现有的混合召回（`core/memory/recall.ts`）是**同一条路**：
> 现在它按重要度 + 关联度从全量里挑；加索引之后，挑的范围从「全部 590 条」变成
> 「50 条印象 + 命中的原文」，精度与成本同时改善。

## 五、记忆对性格与情感的影响，以及回滚（问题④）

现状：每轮会推演情绪与关系（`memory/affect.ts`），写得进、看不出、也撤不干净。
建议三条：

1. **影响必须是「记录」而不是「直接改数」**：每次记忆影响性格/情感时，落一条
   `AffectChange { targetInstanceId, before, after, reason, sourceMemoryIds, createdAt }`。
   它只追加、不覆盖——**能不能回滚，取决于原来的值有没有被记下来**。
2. **回滚有两条粒度**：① 按轮回滚（已经有了：归档 / 重抽会回滚情绪与关系）；
   ② **按条目回滚**（新）：在记忆面板的「影响」里点「撤销这条影响」，
   把关系值改回 `before`，并把这条变更标成 `reverted`（不删，留痕）。
3. **不可逆的点只有一处**：`deletedAt` 的软删除与合并的「已被取代」——
   两处都保留原文，所以任何一条影响都能找到它的来源与当时的数值。
   UI 上要能一眼看到「这条印象是由哪几条记忆合并来的」。

## 六、拆成能做的步子（顺序 27a–27e）

| 顺序 | 做什么 | 为什么排在这儿 | 验收 |
| --- | --- | --- | --- |
| 27a | 记忆合并（合并低重要度、同视角、时间相邻的；原文标 `supersededBy`） | 记忆池是根，先收住它 | 内核单测 + 300 轮实测：记忆条数从 ~2/轮降到目标线以下，且随便点一条印象能找到原文 |
| 27b | 新对话的「记忆附件」（关系现状 + 时间线索引 + 记忆索引）并写进角色卡附件字段 | 有了印象才能生成索引 | 开新对话时附件 ≤ 1,600 字；索引里能看到原对话的线索 |
| 27c | 关键词触发的按需检索（索引命中 / 意图命中才注入正文） | 附件不臃肿的前提 | 日常闲聊的提示词**不增长**；提到关键词时对应正文出现在提示词里 |
| 27d | 影响记录与按条目回滚 | 有了它才敢让记忆改性格 | 面板能撤销一条影响，关系值回到 `before` |
| 27e | 面板与文档（索引视图、印象的来源链、TASKS/EVAL 记录） | 收尾 | 真机走一遍：老对话 → 建附件 → 新对话提到旧事 → 角色接得上 |

**为什么先 27a**：另外四步都以「记忆有层级」为前提；不做合并，索引就是把 590 条平铺一遍，
照样臃肿。而且 27a 一个人也能验（单测 + 长跑数字），不依赖界面。

## 八、2026-09-21：默认值改成「够 800 条用户输入」，27a 开工

用户要求把**默认的上下文窗口与回复预留**改成满足 800 条用户输入，并且明确「不用再测一次」。
改动与它的代价：

| 改哪儿 | 原来 | 现在 | 为什么 |
| --- | --- | --- | --- |
| `createProviderProfile` 的 `maxTokens` | 16384 | **65536** | 800 轮 ≈ 59k token + 固定部分（系统提示/卡/场景/记忆索引）≈ 3k，合计约 62k；65536 是 **DeepSeek-chat 自己的真实窗口**，再多就会把用户推到一个「模型根本不接受」的数字上（128k 的模型可以自己调） |
| `reserveForReply` | 1024 | **4096** | 一句一千字的回复也就 ~500 token，4k 是宽裕余量；原来那 1k 在长回复时会被顶到边 |
| 装配的 `historyLimit` | `?? 40` | `?? 3000` | **这才是原来真正卡住长对话的地方**：窗口调多大都只带最近 40 条消息。现在让**窗口**当约束，超了由预算守卫**从最旧的历史开始丢** |
| 老库里的配置 | — | 迁移 v7：**只升级还是老默认值（16384/1024）的那份** | 用户自己调过的数字不许动——「帮你优化」最讨人厌 |

**实测确认**（60 轮，只做小规模确认，没有重跑长对话）：

```
第 1 次 1001 字 → 第 30 次 ~4300 字 → 第 60 次 6845 字（还在长）
对照：历史上限还是 40 条时，第 60 轮是 3733 字且从此不动
```

**代价必须说清楚**：提示词现在会**随对话长上去**（直到窗口填满）。800 轮时每轮大约要发
6 万 token 的输入，按便宜档位约 **0.12 元/轮**——聊满 800 轮大约 **100 元**，
而按老设置（每次只带最近 40 条）是 **2 元**。这是「满足 800 条」的直接代价，
也**正是第 27c 步（索引化按需检索）存在的理由**：等记忆索引上线之后，
近处历史可以重新收窄，远处的事靠命中索引取——两边的钱都省。

### 27a 已落地：从「决定合并哪些」到「真的压出印象」

`packages/core/src/memory/consolidate.ts`：

| 函数 | 做什么 |
| --- | --- |
| `isConsolidatable(memory, minImportance)` | 这条能不能参与：低重要度、没钉住、没锁、没删、没被合并过 |
| `planConsolidation(memories, options)` | 按**视角 + 对话**分组，攒够阈值才动手；从**最旧的一段**开始切；时间隔超过 6 小时不放进同一批 |
| `buildConsolidationPrompt(group, memories)` | 给模型的那段提示词：只要求压成 1–3 句事实，不抒情、不编细节 |

阈值与实测挂钩：**同视角低重要度（≤0.4）攒到 40 条**才开始合并，
一次最多压 40 条、一次最多两组——因为 300 轮 590 条里绝大多数正是这类「日常经过」。
**7 个单测**盯的是「挑错人」这类看不出来的错：不混视角、跳过钉住/高重要度/墓碑、
先合并最旧的、时间隔远了分批、提示词按时间排序。

**第二步（已落）**：接进后台队列。每轮结算后按「每 20 条记忆」排一次队
（幂等键带桶号，同一批只排一次；攒不够时那一趟是空跑、不发调用）；
runner 拿到**最新**记忆再决定合并哪一组（与场记同一个套路：界面只负责「来看一眼」）。

真机演练（50 轮 + 假模型，读 IndexedDB 对账）**5/5**：

```
记忆总数 101：印象 1 条，被盖章的原文 20 条
对账：印象要求 20 条 → 实际盖章 20 条；差 0 条
PASS  出现了合并出来的「印象」
PASS  原文被盖上「已被取代」的章
PASS  原文一条都没删（软删除字段仍是 null）
PASS  印象带得回来源（supersedes 指向原文）
PASS  没有页面级错误
```

**演练抓到一个真 bug（已修）**：第一次对账时「印象要求 20 条 → 实际盖章 9 条」。
原因是**回想记账那一步把整条记忆用旧拷贝写了回去**——`markRecalled` 手里那份是
装配提示词时读到的快照，中间隔着一次模型调用，于是刚盖的章被静默抹掉。
修法：新增 `Repository.markMemoriesRecalled(ids, at)`，**先读最新再只改那两个字段**；
原来的整条写回不再使用。回归测试写在 `core/storage/recall-stamp.test.ts`。

**27b 第一步（已落）**：`core/memory/attachment.ts`——三层附件的数据形状与生成。

| 层 | 内容 | 预算 | 超了怎么丢 |
| --- | --- | --- | --- |
| ① 关系现状 | 由信任/亲近/恐惧/紧张换算成**一句话**（「他挺亲近你，信得过你」） | ≤ 60 字 | 不会超 |
| ② 时间线索引 | 每章一行：**标题 + 关键词 + 半句话** | ≤ 600 字 | 丢**最早的**章（最近的几章对新对话更有用） |
| ③ 记忆索引 | 每条印象一行：**关键词 + 半句话** | ≤ 1,000 字 | 丢**重要度最低**的 |

关键词是**启发式**（免费、够用）：调用方给的词（参与者名、地点、章标题）+
文本里成对引号中的专名（「胡记院」）+ 出现两次以上的 2–4 字片段（「账房」）。
将来换成模型生成也只改这一个函数。

三条约束都写进了代码注释与单测（7 个）：**纯函数**（不调模型、不碰库）、
**丢了要如实记账**（`stats.dropped`——用户看到「带了 40/59 条」比看到静悄悄缩水好）、
**附件里不放原文**（只放关键词 + 半句话，正文留给 27c 按需展开）。
附带 `readAttachment` / `withAttachment`：附件挂在 `Card.extensions['dramatis.memoryAttachment']`，
**跟着角色卡走**（本机与同步都跟着）。

**27b 第二步（已落）**：`buildCardMemoryAttachment` 把「卡在原世界的实例、原对话章节、该实例的印象」接起来；开新对话时由 `startConversation` 自动写回 `Card.extensions`，界面提示「从《原对话》带去 N 条印象 / M 章，丢了 X 条」。没有合并印象时，退回尚未被取代的高重要度条目；没有材料时不造空附件。无头真机 7/7，单测总数 540。
**27c（已落）**：装配时只常驻 `renderAttachment()` 索引；命中索引关键词或问过去时，`expandAttachment()` 才展开最多 3 条正文。无头假模型实测：日常 1,022 字、命中 1,253 字，增量 231 字（≈116 token）。演练发现旧记忆还会从普通召回漏回来，已把常规召回限定在当前对话，旧对话只经附件取用。
**27d（已落）**：`AffectChange/RelationshipChange` 带 `id`、实际 before/after、`sourceMemoryIds` 与 `reversionOf`；逐条撤销只追加反向记录，原记录不改，回合级回滚也走同一路径。迁移 v9 从当前值反向回放旧 delta；无头真机 9/9。
**27e（已落）**：记忆面板显示来源链与附件预览；`resolveMemorySources()` 解析 `supersedes`，找不到的来源如实记账。全链路真机 6/6。当前关键词仍是启发式，只出现一次且未被参与者/地点带出的词不会进索引。
**下一步（27b 第二步 + 27c）**：开新对话时把原对话的章与印象喂给 `buildMemoryAttachment`，
把结果挂到卡上；装配提示词时先只注入**索引**，等对话里出现关键词再展开命中的两三条正文。

这次的三条读数（都写在上文）：**提示词第 60 轮封顶 3,754 字**、
**记忆 2 条/轮线性增长**、**300 轮 ≈ 93 万 token ≈ 2.2 元**。
