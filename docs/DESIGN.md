# Dramatis 设计文档

本文档描述 Dramatis 的目标、核心概念模型与关键技术方案。实现过程中如有偏离，以本文档为准并同步更新。

## 1. 设计目标与非目标

### 目标

- 兼容 SillyTavern 生态，用户的角色卡、世界书、预设不必重买重做。
- 把"谁在场、记得什么、为什么这么说"从模型黑盒里取出来，变成用户可掌控的系统。
- Web / Android / 桌面三端，账号与云同步，模型接入由用户自带 Key。
- 长期运行不崩：内存、上下文、成本都要有上限。

### 非目标

- 不做 SillyTavern 的分支或替代品，也不追求 UI 层面的功能对齐。
- 不做托管算力，不代付模型费用。
- 不做社区与角色卡分发平台（至少 M5 之前不考虑）。

## 2. 核心概念模型

### 2.1 角色卡与角色实例必须分离

这是整个设计的地基。SillyTavern 中一张卡就是一个角色，所有聊天共用同一份状态，因此无法表达"这个世界线里的他"。

| 概念 | 说明 |
| --- | --- |
| **Card（角色卡）** | 模板。名字、人格、开场白、绑定的世界书。可直接从 ST 生态导入。 |
| **Instance（角色实例）** | 某个世界线中的具体存在。承载与玩家的关系数值、当前情绪与状态、私有记忆库、在场状态。 |

卡可以升级后重新导入，实例的记忆不受影响。没有这个分离，记忆与人格演化都无从谈起。

### 2.2 世界与场景

| 概念 | 说明 |
| --- | --- |
| **Room（世界 / 房间）** | 一条持续的世界线。持有角色实例集合、世界书、预设、玩家 persona。 |
| **Scene（场景）** | 有地点、时间、在场名单的一段连续叙事。是导演系统的作用对象。 |
| **Turn（回合）** | 玩家输入到角色回应的一次完整往复。 |

场景是记忆固化的边界：场景结束时，把这一段的经过沉淀成事件条目。

### 2.3 入场策略与存在模式

两个正交的概念，不要合并。

**Cast Policy（场景的入场策略）**

| 值 | 行为 |
| --- | --- |
| `open` | 满足触发条件的角色可自行入场 |
| `locked` | 冻结在场名单，AI 不得引入任何新角色 |
| `invite_only` | 只有玩家显式召唤才入场 |
| `triggered` | 满足条件才入场（角色目标被触发、世界书关键词命中） |

**Presence（角色的存在模式）**

| 值 | 在场 | 可发言 | 记忆积累 | 典型用途 |
| --- | --- | --- | --- | --- |
| `onstage` | 是 | 是 | 是 | 常规在场 |
| `muted` | 是 | 否 | 是 | 沉默的观察者，存在感本身就是戏 |
| `offscreen` | 否 | 否 | 是 | 幕后生活，重新入场时接得上 |
| `absent` | 否 | 否 | 否 | 彻底离场 |

`offscreen` 是叙事质量的关键。角色重新入场时，自动生成一段"这段时间他在做什么"的填充记忆，避免人物像被冻结了一样。

## 3. 导演系统

### 3.1 调度信号

发言调度独立于生成模型，输入信号至少包括：

- 玩家消息是否点名、是否指向特定角色、是否公开提问
- 角色名与世界书关键词命中
- 与各角色当前目标的相关度
- 召回记忆与当前话题的相似度
- 角色的外向权重（慢变量中的外向轴）
- 冷却惩罚：刚发过言的角色降权
- 公平性补偿：久未发言的角色升权
- 存在模式与情绪状态（`muted` 永不入选；情绪低落时降低主动发起概率）

输出为有序的发言者列表，长度可以为 0（没人接话也是一种表达），并为每个发言者标注意图。

### 3.2 意图先行

生成对白之前，先让角色输出一句"此刻想做什么"的意图，再据此生成正式内容。收益：

- 插话、抢话、欲言又止、故意回避等行为才可能自然出现
- 出问题时能定位到是调度层、意图层还是表达层

### 3.3 成本控制

调度与意图判定可以用便宜模型或纯规则完成，只有正式对白用主模型。BYOK 场景下这直接决定用户是否用得起。

## 4. 记忆系统

### 4.1 分层

| 层 | 内容 | 精度 | 生命周期 |
| --- | --- | --- | --- |
| 工作记忆 | 最近 N 轮原文 | 精确 | 滚动窗口 |
| 场景记忆 | 当前场景的滚动摘要 | 中 | 随场景 |
| 情节记忆 | 结构化事件条目 | 中高 | 长期，可检索 |
| 语义记忆 | 客观事实与世界设定 | 高 | 长期 |
| 关系情绪 | 角色→玩家、角色→角色的慢变量 | 数值 | 长期，会衰减 |
| 人物内核 | 当前场景激活的性格切片 | 高 | 随场景 |

### 4.2 按视角存储

同一件事，不同角色记下的内容应当不同。写入事件时，为每个在场者生成以他视角为准的条目，记录他注意到了什么、误解了什么、在意什么，以及他对关系的影响判断。

这是"多个角色"与"一个角色的多个分身"之间的分界线，也是本项目的核心差异点。

### 4.3 事件条目结构

```
Event {
  id, roomId, sceneId
  timeline: { worldTime, sequence }
  location, participants[]
  summary            // 客观经过
  observerId         // 该条目属于谁的视角；主观条目必填
  perception         // 该视角下的观感、误解、情绪反应
  importance          // 0~1，影响召回优先级与衰减速度
  affects[]          // 涉及的关系边与变化量
  sourceTurnIds[]    // 溯源，可展开回原文
  createdAt, lastRecalledAt, recallCount
}
```

### 4.4 召回

混合检索，而非纯向量：

```
score = w1 · 向量相似度
      + w2 · 关键词 / BM25
      + w3 · 重要性
      + w4 · 时效（近期加权，久远衰减）
      + w5 · 关联过滤命中（涉及在场者 / 当前地点 / 当前时间线）
```

标签过滤先行，把候选限定在与当前场景相关的范围内，再做排序。每个角色有独立的记忆预算（默认约 800 token），按分数裁剪。

除预取外，允许模型主动调用 `search_memory(query)` 深挖。这要求模型支持工具调用，不支持时退化为预取。

### 4.5 压缩与遗忘

**压缩**（有损，但原文永不删除）：

```
轮 → 场景摘要 → 章节摘要
```

触发条件为轮数阈值或上下文占用超阈值。被压出窗口的原文留在本地库，随时可展开回想。

**遗忘**（降低优先级，不删除）：

低重要度且长期未被回想的记忆降低召回权重，也可合并为"很久以前……"的粗粒度印象。这既省 token，也更接近人的记忆方式。

### 4.6 预算守卫

拼装前核算 token 预算，超出时按固定顺序降级：

```
1. 丢弃最旧的工作记忆原文
2. 丢弃低分召回记忆
3. 压缩关系与情绪描述
4. 压缩非发言者的人设描述
```

**任何情况下都要产出可用 prompt**，宁可信息少也不允许因超长而失败。

## 5. 人格与动态状态

### 5.1 两层变量

| 层 | 内容 | 变化速度 |
| --- | --- | --- |
| 慢变量 | 5~8 个可打分特质轴（外向、攻击、共情、戏谑、谨慎等） | 基本恒定 |
| 快变量 | 情绪状态、关系数值 | 每轮更新、会衰减 |

慢变量从角色卡解析而来，允许手动校正。快变量的变化必须记录理由，便于回溯与调试。

### 5.2 状态更新器

每轮生成结束后，以（角色输出 + 玩家回应）为输入推演：

- 情绪变化
- 关系数值变化
- 值得记住的事件

状态更新与事件抽取是额外调用，因此必须**异步跑到后台**，不阻塞对话回合；并提供"后台任务使用便宜模型"的独立配置。

### 5.3 抗漂移

长对话的常见退化：所有角色逐渐收敛为同一个温柔知心的助手腔。对策是每隔 N 轮用角色卡内核重新锚定一次，并对慢变量施加向原始设定的回归力。

## 6. Prompt 装配流水线

顺序固定、模块可插拔：

```
1. 系统指令与风格预设（兼容 ST 预设）
2. 世界书条目（常驻 + 触发命中）
3. 在场角色内核切片（发言者完整，非发言者一句话速写 + 对玩家的态度）
4. 关系与情绪状态块
5. 召回记忆块（按角色分组，标注"这是你知道的事"）
6. 场景摘要 + 近期原文
7. 发言者指令（轮到谁、意图是什么）
8. 玩家输入
```

多角色场景的成本大头在第 3 项。**发言者给完整内核，非发言者只给速写**，否则 token 会瞬间爆炸。

## 7. 多端架构

### 7.1 仓库结构

```
packages/core       数据模型 / 调度器 / 记忆检索 / prompt 装配（纯 TS，无平台依赖）
apps/web            React + Vite
apps/desktop        Tauri
apps/android        Capacitor
services/sync       账号与云同步
```

`core` 通过 adapter 抽象数据库、文件系统与网络，保证三端复用同一套核心逻辑。

### 7.2 平台选型

| 端 | 方案 | 理由 |
| --- | --- | --- |
| Web | React + Vite | 也是桌面与移动端的渲染层来源 |
| 桌面 | Tauri | 体积远小于 Electron，可调用本地模型，具备文件系统权限 |
| Android | Capacitor | 后台任务与通知生态成熟；Tauri 移动端更省代码但插件较弱 |

三端共用一套 React UI，外壳不同。

### 7.3 本地存储

统一走 SQLite：原生端用 SQLite，Web 端用 SQLite WASM + OPFS。通过 Drizzle 或 Kysely 维护单一 schema，避免三套数据层。

## 8. 账号与同步

### 8.1 本地优先

本地库是唯一真相源，云端是增强。断网、服务端下线都不影响使用。

### 8.2 同步协议

- 每个实体携带 `id (uuid)`、`updatedAt`、`deletedAt`（软删除）
- 服务端分配单调递增 `rev`，客户端按 `rev` 增量拉取
- 聊天消息 append-only，天然几乎无冲突
- 角色状态与记忆的冲突用 LWW 处理，但**冲突的记忆都保留**——多记一点，用户能接受

### 8.3 密钥与隐私

- API Key 存在设备安全存储（Keychain / Keystore / DPAPI），**不参与同步**，换设备重新输入
- 可选的端到端加密同步：用同步密码派生密钥，服务端不接触明文
- 后端不代理模型请求，流量由客户端直连模型服务商

## 9. SillyTavern 兼容层

### 9.1 必须支持

| 对象 | 格式 |
| --- | --- |
| 角色卡 | PNG 的 `chara` / `ccv3` tEXt 块，以及 V2 / V3 JSON |
| 世界书 | `world_info` JSON，含键位、插入位置、递归、概率等字段 |
| 预设 | sampler 参数与 prompt manager 结构 |
| 聊天记录 | `jsonl` 导入导出 |

### 9.2 降级原则

无法支持的字段必须**显式提示并给出降级结果**，不允许静默丢弃。用户需要知道哪些内容没能带过来。

## 11. 路线图

| | 内容 | 目的 |
| --- | --- | --- |
| M0 | 数据模型 + ST 卡/世界书导入 + 单人对话跑通 | 验证兼容层 |
| M1 | 场景与导演系统（拉人 / 锁场 / 驱逐 / 调度） | 核心玩法成立 |
| M2 | 记忆系统（事件抽取 → 分层摘要 → 混合召回 → 预算守卫） | 长线不崩 |
| M3 | 人格 / 情绪 / 关系动态 + 抗漂移 | 角色不趋同 |
| M4 | 账号 + 云同步 + 三端打包 | 多端落地 |
| M5 | 房间与角色卡导出、小圈子邀请 | 分享 |

建议先做 M0 + M1：记忆系统的参数必须拿真实对话流来调，过早优化检索是空转。
