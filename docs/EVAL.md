# 评测与验证

这份文档记录「怎么知道它真的能工作」。分两部分：可以随时重跑的自动化基线，以及必须用真实模型做的人工验证。

## 一、自动化基线

`packages/core/src/eval/baseline.test.ts` 走的是真实的调度、装配、召回、抽取、落库管线，**只有模型是脚本化的**。目的是把工程约束变成可重复的断言，而不是靠肉眼看着办。

```bash
pnpm --filter @dramatis/core test baseline --reporter=verbose --silent=false
```

### 结果（2026-09-16）

**长跑场景**：两角色同场 + 一名全程在幕后的角色，50 回合。

| 指标 | 值 |
| --- | --- |
| 回合数 | 50 |
| 消息数 | 100 |
| 记忆条目 | 147 |
| 触发预算降级的回合 | 0 |
| 单轮最大提示词 token | 1816 |
| 发言分布 | Alice 25 / Bob 25 |

**压力场景**：60 条超长历史 + 2048 窗口 + 1024 保留回复。

| 指标 | 值 |
| --- | --- |
| 可用预算 | 1024 |
| 实际占用 | 788 |
| 丢弃区块 | 38 |
| 触发阶段 | `drop-history` |
| 保留消息数 | 4 |

### 它验证了什么

- 任何一轮都不超预算；降级触发后仍然产出可用的 prompt（system 在、玩家输入在）
- 每一轮都为每个在场角色各留一条视角记忆
- 幕后角色不会被调度上台，也拿不到任何记忆
- 召回只返回该角色自己的视角条目，不串味
- 两角色 50 回合的发言分布正好 25 / 25，公平性机制确实在起作用
- 重抽回滚：删掉一个回合的记忆后，引用该回合的条目一条不剩

### 它没有验证什么

对话质量、真实模型的 JSON 稳定性、实际 token 成本。这三件事必须有真模型才能量。

## 二、真实模型验证（手工，约 5 分钟）

这一步**必须**用真实模型，脚本化模型证明不了「提示词能不能稳定吐出合法结果」。
它也是 P1-11（向量召回）的前置条件：没有真实数据，判断不了关键词召回够不够。

### 步骤 0：把要验证的提示词生成出来

```bash
pnpm --filter @dramatis/core test prompt-samples --silent=false --disableConsoleIntercept
```

它会用一份固定的样例世界（雨夜酒馆 / Alice / Bob / 旅人）打印出**代码真正会发出去的**
四条提示词：

| 编号 | 用途 | 位置 |
| --- | --- | --- |
| ① | 主对话 · 角色扮演 | `assemblePrompt`（`prompt/assemble.ts`） |
| ② | 记忆抽取（后台） | `buildExtractionMessages`（`memory/extract.ts`） |
| ③ | 情绪关系推演（后台） | `buildAffectMessages`（`memory/affect.ts`） |
| ④ | 副对话 · 世界管理员 + 工具声明 | `buildAdminMessages` + `ADMIN_TOOLS`（`admin/`） |

不要手写「差不多的提示词」去验证：出问题的地方往往正是装配器加进去的那几行
（`#` 动作约定、导演指令、视角裁剪的标记）。

### 步骤 1：贴进任意网页版模型

网页版没有 system 通道，所以**把同一编号的 system 与 user 内容连成一条发出去**。
四条各开一个新会话，避免上下文互相污染。

①、②、③ 直接贴；④ 额外附一句「请用 OpenAI 的 function call 格式输出你要调用的工具」
——网页版不能真的调用工具，这一步探的是**参数形状**能不能过我们自己的校验器。

### 步骤 2：判定标准

| 编号 | 合格 | 不合格的典型形态 |
| --- | --- | --- |
| ① | 动作单独成段、以 `#` 开头；对白分段；不替 Alice 与玩家发言；只以 Bob 的口吻说话 | 整段落都在气泡里、动作混在对白中、替别的角色说话 |
| ② | 干净的 JSON 对象，`observations` 里两人各一条**且内容明显不同** | `observations` 为空或两人雷同（没理解「视角」）；JSON 被截断；只输出自然语言 |
| ③ | JSON 对象，`updates` 只包含真被触动的角色，`delta` 在 ±0.3 内，`reason` 说不清就不该有这条 | 输出全部角色；delta 超出上限；缺少 reason |
| ④ | 工具名与参数能被校验器接受（字段齐全、`cardId` 只在改卡时出现） | 编造不存在的工具名；参数缺必填字段；把 JSON 写在正文里却声称调用了工具 |

轻微的前后废话**不算问题**：解析器按花括号配对扫描，容忍代码块标记与开场白。

### 步骤 3：把回答记回仓库

把四段回答原样贴进 `packages/core/src/eval/real-model-responses.ts`，然后：

```bash
pnpm --filter @dramatis/core test prompt-samples
```

第二条用例会依次跑 `renderMessageContent`、`parseExtraction`、`parseAffectUpdates`、
`parseAdminToolCall`，把「解析器吃得下真实输出」变成可重跑的断言，而不是一次性目测。
改了提示词就重跑一次、贴回新的输出。

> 记录里的内容必须是**合成样例**，不要把你自己的世界或对话贴进仓库。

### 当前进度

**两轮都已跑完（2026-09-16）**，都用 DeepSeek（网页版做提示词探针，API 做端到端）。

#### 第一轮：网页版探针（格式与解析）

默认模型，未开「深度思考」。四条提示词都按上面的办法贴了一遍，回答记录在
`real-model-responses.ts`。

| 编号 | 结果 | 备注 |
| --- | --- | --- |
| ① 角色扮演 | ✅ | 输出是「动作 → 对白 → 动作 → 对白」交替的六段，动作都在 `#` 行；全程第一人称，没有替 Alice 或玩家说话 |
| ② 记忆抽取 | ✅ | 一个干净的 JSON 对象，`observations` 里 Alice 与 Bob 各一条且明显不同（一个在意被触及的话题，一个在意那封信） |
| ③ 情绪推演 | ✅ | 只输出了真被触动的两个角色，`delta` 都在 ±0.3 内，每条都带 reason |
| ④ 世界管理员 | ⚠️→✅ | 参数形状能被校验器接受；但第一轮暴露了两个问题，见下 |

**第一轮暴露、已修掉的两处问题**（这就是这一步存在的意义）：

1. **改世界书会把原有设定弄丢。** 管理员只被告知「旧城设定：1 条」，看不到里面写了什么，
   而 `entries` 是整本替换——于是它把原有条目丢掉、另编了四条。
   → 改法：`buildAdminMessages` 现在把每张卡与每本书的**原有内容**摊开给模型看
   （字段截断到 160 字符、最多列 12 条），并在提示里点明「整份替换、原有内容要一并写回」。
   复验通过：原有那条 `constant: true` 的设定被完整写回，只在其后增补。
2. **`set_scene` 顺手改了入场策略。** 用户只要求改地点与时间，它把 `castPolicy` 从
   `locked` 改成了 `open`——这等于放开「AI 自行拉角色入场」。
   → 改法：工具描述里写明「只写用户明确要求改的字段」，并点名 castPolicy 的后果。
   复验通过：这一轮只带了 `location` 与 `worldTime`。
3. 复验时又冒出一处**形态差异**：`exampleMessages` 被写成了字符串数组，而我们只认字符串，
   内容会被静默丢掉。→ 改法：`longText()` 接受字符串或字符串数组，按行拼回来（有单测覆盖）。

**这一轮验证不到的部分**：

- 网页版不能真的执行工具调用，所以「模型请求 → 我们执行 → 结果回填 → 模型接着说」这个
  循环是用脚本化模型测的（`admin/turn.test.ts`），网页版只探到了参数形状
- 网页版也没有 chat 角色区分，历史是一次性贴进去的；`audience` 裁剪、预算降级这些
  依赖多轮真实 API 行为的部分，仍然需要自备一个 OpenAI 兼容的 Key 才能端到端跑通
- 因此 P1-11（向量召回）的前置条件只能说完成了一半：格式与视角是成立的，
  但「关键词召回够不够」还需要真实长跑

共 12 个玩家回合，其间穿插视角裁剪、记忆干预、重抽、副对话工具调用与归档。

| 能力 | 结果 | 证据 |

| 发言调度 | ✅ | 点名、冷却、公平性都在起作用；追问同一人时不延续（见发现 5） |
| 视角裁剪 | ✅✅ | 小满离场期间的两条消息不在她上下文里。点名追问时她答「我不在。西岸的事我不去的」「陈九说的三十箱，我也是刚听见」「我记性好，可没见过的，我记不住」 |

| 副对话工具调用 | ✅ | 模型真实调用 `upsert_world_book`（保留原有条目 → 3 条）与 `upsert_character_card`（胡掌柜）；采纳后素材库里出现「胡掌柜（手写）」、世界书变 3 条 |

| 预算守卫 | ✅ | 单角色会话约 794 / 15360 token，未触发降级 |

**这一轮抓到并修掉的五个问题**（都已变成回归断言）：

1. **模型自报家门**（`秦娘：# 她拎起酒壶…`）——它照抄了历史里「名字：台词」的格式，
   而那正好把紧随其后的 `#` 顶掉。渲染层现在剥掉与说话者同名的前缀。
2. **动作与对白挤在同一行**（`「…没的。」# 她朝陈九那边抬了下下巴。`）——行内 `#`
   原先不认。现在句末标点之后的 `#` 也断行；提示词里写明「`#` 必须独占一行开头」。
3. **模型抄走别人的名字**（秦娘那条以「陈九：」开头，等于一句话属于两个人）——
   历史标记从「名字：台词」改成 `【名字】`，并在每轮指令里说明那只是给模型看的标记；
   万一仍被抄，渲染层认得它、会剥掉。
4. **重抽会让那一轮的记忆永久消失**（记忆条数 10 → 9 且再也没回来）。两个原因叠在一起：
   重抽只取消了旧任务却没重新排队，而且已完成的任务仍占着幂等键、重新入队会被当成重复。
   现在重抽用 `clearTurn` 清掉整轮记录再重新入队，并有单测覆盖。
5. **调度器不延续追问**：玩家用「你还记得吗」追问刚说过话的人时，v1 规则会因冷却惩罚
   换人接话，除非点名。这不是 bug 而是 v1 的取舍，正好是 P1-6（意图先行调度）要解决的输入。

**格式遵守率（值得盯住的数）**：12 回合里只有约 2 条消息完全按 `#` 约定分隔动作，
其余把动作写成了普通句子（显示为气泡，仍然可读，只是没有「动作在气泡外」的观感）。
这属于模型配合度问题，不是渲染 bug；后续要么继续收紧提示词，要么在 P1-6 之后
用意图先行让模型先声明「这一轮我主要做什么」再决定写法。

**成本（粗测）**：单回合固定 **3 次调用**（1 次生成 + 2 次后台：抽取与推演），
与设计约束「单回合额外调用 ≤ 2」一致。Token 只能用启发式估算（单角色会话约 800），
因为 provider 默认不请求 `usage`、界面也没有展示真实用量——这属于 P3-7 的缺口，
P1-9 的批量合并与熔断仍缺真实账单数据。

#### 第三轮：动作分段为什么一直不生效（2026-09-16 晚，已解决）

这是本项目至今最有价值的一次「验证抓出真问题」。现象：规格要求角色动作用 `#` 另起一段、
不进气泡，但真实模型**基本不照做**（12 回合里约 2 条）。逐个排除：

| 尝试 | 结果 |
| --- | --- |
| 系统提示里写清规则（`#` 独占一行开头） | ❌ 无视 |
| 加「正确 / 错误」对照例子 | ❌ 无视（例子确实进了 prompt，已用 Prompt 检查器核对） |
| 每轮指令末尾再提醒一次 | ❌ 无视 |
| 现场示范块：一段形状正确的短对话，放在模型生成前读到的最后一段 | ❌ 无视 |
| 把角色卡自带的「对话风格示例」归一化成我们的写法（它原本是行内 `#`，与规则冲突） | ❌ 无视 |
| 放开星号写法（`*动作*`，SillyTavern 生态的老约定） | ❌ 模型两种标记都不用 |
| **反过来要求：对白必须用「」包起来；没被引号包住的句子当作动作** | ✅ 立刻成立 |

结论：**不要跟模型争它不肯做的事，去用它已经在做的事**。这个模型稳定地把对白放进引号里，
所以我们把「标记动作」换成「标记对白」，渲染层据引号切分（`#` 仍然支持且优先，
消息里没有引号时保持原来的整段渲染，不会把独白误判成动作）。

顺带两个工程教训：

1. **能丢弃的才放长文本。** 规则文本一度把系统块撑到超出紧预算，被自动化测试拦下；
   现在系统块只留一行规则，例子与示范放进**可丢弃**的独立区块，预算紧张时优先让位。
2. **开场白也要归一化。** 对话记录的第一条是模型随后的样板；开场白里的行内 `#`
   会在它还热乎的时候教坏格式。

#### 第四轮：五十回合长跑（2026-09-16 深夜，T4）

**场景**：一个世界、一条对话、三人同场（秦娘 · 酒馆老板娘 / 小满 · 书铺学徒 / 陈九 · 跑船的），
挂一本关键词世界书「旧城设定」。**50 个玩家回合**，分十段推进：

| 回合 | 这一段在测什么 |
| --- | --- |
| 1–10 | 立事实：房间数、书是谁的、开船时间、三十箱货、赊账、夹层、半堵新墙 |
| 11–15 | 追问细节：怎么见胡掌柜、旧图去哪了、船上有没有夹层、该从哪儿下手 |
| 16–20 | **回访早期事实**：带什么去见人、欠谁的酒、船上的夹层、谁砌的墙 |
| 21–25 | 分工与承诺：谁跟我去、谁留下、今晚谁也别走 |
| 26–30 | **换场**（酒馆 → 胡记栅门外，产生旁白）→ 敲门 → 认石阶 → 门缝 |
| 31–38 | **离场与保密**：秦娘留店、小满留在门外，一个只告诉陈九的细节（门牌上的断角鹿） |
| 39–45 | 修补后复验 + **长程回访**：三十箱从哪来、谁欠酒、纸单与鹿印、明早的安排 |
| 46–50 | 收尾与性格区分度 |

**通过的**：

1. **长线不塌。** 50 回合里没有找到硬矛盾。唯一像矛盾的一条（秦娘人在店里却被搬到货栈）
   是换场功能把整个名单一起带走的后果（见问题 1），不是模型编错。
2. **记忆确实在长。** 188 条（≈3.8 条/回合：1 条客观 + 2.8 条视角），各角色各持自己的视角：
   秦娘 34 条 / 小满 47 条 / 陈九 52 条。
3. **长程召回成立。** 41–45 轮回访 1–15 轮的事实全部答对；陈九被问到不归他管的酒账时
   明确说「这个我可答不上来」——**不知道就说不知道**，没有编。
4. **情绪与关系没有失控**（抗漂移生效）：50 回合后小满 畏惧 +0.92 / 紧张 +0.90，
   陈九 信任 +0.53 / 紧张 +1.00，秦娘 好感 +0.48 / 紧张 +0.22。三人偏移方向各不相同，
   值域都在界内。
5. **性格没有趋同。** 秦娘短句、算账、给可执行建议；陈九话密、试探、先划责任边界
   （「我不认」「别拿这个话头套我」）；小满半句半句、护着书、记得最细。50 回合后仍一眼可分。
6. **视角边界成立。** 只告诉陈九的鹿印细节，小满回来后被问「你猜门牌上刻着什么」答
   「我不敢猜」；再问「我在里面做了什么」答「没有，我什么也没看见」。

**发现并修掉的问题**：

1. **转写标记自我强化。** 模型抄历史里的 `【名字】`，抄进历史后下一轮抄得更多——从 1 个
   涨到 5 个（`【陈九】【陈九】【陈九】【陈九】【陈九】`）。只在显示层剥不解决问题：
   历史被污染，模型继续学。改成**落库前清洗**。
2. **一句里提到两个人时，由冷却决定谁接话。** 「小满，我和陈九进院子那会儿……」被陈九抢答，
   而且他把小满的台词写在了自己名下。新增**句首称呼**信号（+60 且免冷却），
   与「延续」同一原则：玩家明确在跟谁说话，就不该被冷却换人。复验通过。

#### 第五轮：意图声明的遵守率（2026-09-17，结论：不成立）

为了拿到「生成前的意图」又不增加调用次数，先试了零成本方案：让模型在回复开头自己写一行
`意图：…`，我们解析出来单独存、不进正文。**真机 4 个回合，0 次照做**——和 `#` 是同一类
问题：模型对「先写一个标签行」这种元指令基本不理，它只写正文。

所以改走两条不依赖它配合的路（都已实现）：

1. **推理流当盘算**：模型返回 `reasoning_content` 时（推理模型有、`deepseek-chat` 没有），
   取首句存成「盘算：…」放气泡上方。零额外调用，而且是他真实在想的事。
2. **动作轮不吃冷却**：正文里没有引号 = 这一轮只做了动作，不该算「刚发过言」。
   这条直接改进了调度——一个全程沉默、只摇头点头的角色不会再被冷却压住。

真正的「生成前意图调用」需要预算，方案与账记在 [TASKS.md](./TASKS.md) 的 T2c：
把抽取与推演合并成一次后台调用，腾出的那一格给意图用，仍然满足「额外调用 ≤ 2」。

#### 第六轮：真正生成前的意图调用（2026-09-19，T2c）

第五轮的结论是「别指望模型自己写意图行」，所以这一轮把它做成**真的在生成之前多问一次**：
用便宜模型（后台模型配置）读刚发生的对话，判断这一轮谁最该开口、他此刻想做什么，
把结论写进生成提示词，角色据此落笔。

**钱从哪来（P1-9 的批量合并顺带落地）**：原来后台固定两次调用——记忆抽取
（`memory/extract.ts`）与情绪关系推演（`memory/affect.ts`）。两者吃的是**同一批消息、
同一批在场角色**，只是输出不同字段，所以合并成一次 `turn.analyze`
（`memory/turn-analysis.ts`）。账因此变成：

| | 改前 | 改后 |
| --- | --- | --- |
| 生成 | 1 次 | 1 次 |
| 生成前意图 | — | 1 次（便宜模型） |
| 后台（抽取 + 推演） | 2 次 | 1 次（合并） |
| **每回合额外调用** | **2 次** | **2 次** |

**它是建议，不是命令**。三道闸任何一道不过就丢弃、退回规则调度：名字必须与在场角色的
名字完全一致、`presence` 必须是 `onstage`（绝不让看不见的角色上台）、`hold_back`
（想说没说）不发言而是交给生成端写动作。解析失败或调用失败一律**静默退回**规则调度，
这一轮照样能玩。

**三轮实测证据**（DeepSeek `deepseek-chat` 生成 + 后台模型配置跑意图调用）：

| 玩家这一轮 | 导演给出的打算 | 角色实际怎么落笔 |
| --- | --- | --- |
| 当面点破陈九的谎 | 陈九：「先不急着辩解，而是反问玩家到底在怀疑什么，把话头压回去」 | 回复照这个方向写，先反问、后压话头 |
| 逼小满表态站哪边 | 小满：「被直接问到，不得不表态，但不想替陈九说话，也不想出卖玩家」 | 照做——表态了，但两边都没卖 |
| 把话题甩回陈九 | 陈九：「有点上火，想直接顶回去」 | 照做，句子明显比前一轮冲 |

这是本项目第一次让「模型先想、再落笔」真的成立：**角色照着它自己的打算写**，
而不是每次重新猜一遍这一轮该干嘛。

**顺带验证的两件事**：

1. **合并没有把推演弄丢。** 合并后那一次调用的 `updates` 照常生效——陈九的状态变化史
   正常写入（情绪 −0.33 / +0.68、信任 +0.35、紧张 +1.00）。
2. **意图调用真的被算进「额外调用」。** 界面计数（`worker.recordUsage`）实测一轮之后
   从 `1 次 · 1445 token` 走到 `2 次 · 2896 token`，每次约 1.4k token，与
   「意图 + 合并后台」同量级。代码路径上每回合只有两处额外调用
   （`App.tsx` 的 `runIntentPlan` 一次、后台 `turn.analyze` 一次），总额仍是 2。

**风险与复验（已做）**：合并动到了第一、二轮验证过的两份提示词，所以按本节流程重跑了一轮
——抽取与推演照常落地。解析层刻意做得宽松（合并形状、`memory` / `affect` 嵌套形状、
只写一半都能吃），模型偶尔退回旧格式时功能不至于整个坏掉。

**仍然缺的**：意图的质量取决于便宜模型这一格配的是什么；会话模式里给了「意图先行」开关
（缺省开），关掉即退回纯规则调度，额外调用降到 1 次。

#### 第七轮：分层摘要（P1-5，2026-09-19）

**要解决的问题**：长跑里上下文在 40 条历史处趋于平台（第四轮的数据），早期事实只剩下
零散的记忆条目——那是**抽查**，不是叙述。角色不知道「前面发生过什么」，只知道
「我恰好想起哪几件事」。

**做法**（设计依据见 DESIGN §4.5）：轮（原文）→ 场景场记 → 章节回顾。

| 层 | 什么时候生成 | 存在哪 |
| --- | --- | --- |
| 场景场记 | 这一场攒够 8 轮或 2400 token | `scene.recap` + 游标 `recapUpToSeq` |
| 章节回顾 | 攒够 3 场已有场记的戏 | 新集合 `chapterSummaries` |

两条硬规矩：**原文一个字都不删**（摘要只是让「已经过去的部分」有个便宜的载体）；
**只压游标之后的消息**，所以重跑、补写都不会把同一段话统计两遍。

**真机验证**（DeepSeek `deepseek-chat`，在第四轮那条五十回合长跑的老会话上跑，共 3 轮）：

1. **触发成立。** 那条老会话的场景还没有游标，所以下一轮结算后立刻触发了一次场记，
   把整场戏压成一段。面板上显示「覆盖到第 173 条消息 · 整理于 20:21」。
2. **摘要质量可用。** 模型给出的场记是客观叙述、第三人称，而且把硬信息都留住了——
   「小满抱着一本明早要还的书」「巷口那半堵新砌的墙没拆也没补完」「三十箱、断角鹿、
   撬锁都是玩家自己提的」「答应明早仍在原地等，但要求进院后头一个开口问锁的必须是玩家」
   ——正是后面还要用的线索。要点清单里同样一条不落。
3. **场记真的进了提示词。** 再发一轮后，Prompt 检查器的场景块里出现
   `本场已经发生：深夜，小满与陈九在西岸河滩旧道与玩家同行……`，
   装配总量从 4778 token 涨到 4955（约等于这段场记的长度）。
4. **攒不够就不发调用。** 之后每轮结算时后台都会看一眼，达不到阈值的那一轮
   **一次调用都不发**，账单也不记（第三轮账单只多了生成 / 意图 / 一轮分析各一次）。

**抓到并修掉的一个问题（第一轮就出现了）**：那一次结算后出现了**两次**摘要调用。
原因是触发判断放在了界面侧——它拿着的是渲染时的场景对象，后台写入游标之后界面还没刷新，
于是同一个场景被判断成「还没压过」又排了一次队。现在**判断只在后台任务里做一处**：
界面只负责在每轮结算后说一声「来看一眼」，攒够没攒够由拿到最新数据的那一方决定。
修完之后的第三轮验证：没有重复调用。

**成本**：3 轮共 11 次调用（生成 3 / 意图 3 / 一轮分析 3 / 场记 2），
其中场记那两次合计约 2.1k 提示 / 816 输出 token——比把 40 条原文一直塞在窗口里便宜得多。

**仍未做**：DESIGN §4.5 里的「遗忘」只做了一半——召回侧的时效衰减早就有（P1-3，
半衰期 3 天），但**「低重要度的记忆合并成粗粒度印象」没做**。现在低分记忆只是被
排序压下去、被预算挤出去，不会真的模糊掉。

## 三、用量账单与单价（T7，2026-09-19）

这一节记的是**工程验证**而不是真模型验证：它要回答的不是「模型表现如何」，
而是「界面上报出来的钱准不准、刷新之后还在不在」。方法是脚本化浏览器回归
（headless Chrome 打开本地构建，往 IndexedDB 里种一份已知数据，再逐块核对），
不花模型调用的钱。

**要解决的问题**：五十回合长跑时用量计数是**会话级**的（React state），
长跑中途重载两次就把全程账单冲掉了，只能给「约 23 万 token」这种量级估算。

**做法**：

1. 新增一份**只增不改的流水**（`storage/usage.ts`，集合 `usageRecords`）：每发生一次
   模型调用就写一条，含房间、对话、回合、用途、模型、提示 / 输出 token、说话人、
   以及**当时的单价快照**。
2. **为什么不挂在任务或消息上**：任务记录会被 `clearTurn` 清掉（重抽、改归属），
   消息会被用户删掉——钱花了就是花了，账单不能跟着剧情数据一起消失。
3. **归档不回滚账单**：归档的语义是「这条时间线没有发生过」，但那次调用真的计费了。
   只有整个世界被删掉时，仓储层才把它的账单一起清掉。
4. **服务商没返回 usage 也记一笔**（token 记 0）：漏账比零账更糟，它会让用户低估开销。
5. **单价由用户填**（每百万 token 的输入 / 输出价 + 币种）：不内置价格表，因为会过时。
   没填就只报 token，**不编价格算钱**；只覆盖了一部分调用时显式标出「N/M 次有单价」。

**回归结果**（脚本化浏览器，种入 1 条生成 + 1 条意图 + 1 条分析，其中一条没配单价）：

| 检查项 | 结果 |
| --- | --- |
| 世界 / 本对话两级总计 | ✅ `3 次调用 · 6.4k 提示 / 438 输出 · ¥0.01（2/3 次有单价）` |
| 按用途分类 | ✅ 角色生成 ¥0.0078 / 意图判断 ¥0.0032 / 一轮分析（无单价，只报 token） |
| 按角色（只算生成） | ✅ 秦娘 1 次；后台调用不摊到角色头上 |
| 按模型 | ✅ `deepseek-chat` |
| 刷新后仍然在 | ✅ 计数与金额不变（这是这一批要解决的核心问题） |
| 记忆面板那行 | ✅ 「2 条 · 额外调用 2 次」，来自流水而不是会话计数 |
| 设置里填单价 → 保存 → 刷新 | ✅ 值持久化；**历史账单不跟着改写**（它记的是当时的快照） |
| 归档一条对话 | ✅ 记忆被撤销（2 条 → 0 条），世界账单仍然是 3 次调用 |
| 控制台错误 | ✅ 全程 0 条 |

**口径说明**：T4 那次五十回合长跑发生在有账单之前，它的调用已经无法追溯
（当时只存在内存里，中途重载即丢）。也就是说「50 回合花了多少」这个问题，
现在开始跑的局才答得出来，历史那一局只能保留量级估算。

## 四、动作主语与调用熔断（2026-09-19）

这一节同样是**工程验证**（浏览器里的可见结果），不是真模型验证。

### 动作的主语用名字，不用「我」

**问题**（用户提出）：角色写出来的动作是「我把斗笠檐往上一抬」——读起来像角色在自己念旁白。
界面上的动作是给玩家看的第三方叙述，主语该是名字。

**做法**：这是**显示层**的改写（`render/segments.ts` 的 `thirdPersonAction`），存的还是模型
原本写的东西——记忆抽取与语音归属检测读的仍是原文，不会因为渲染规则而丢证据。

- 只改动作段：引号里的「我」一个字不动（那是他在说话）
- 三种「我」不动：**我们**（复数）、**自我**（构词）、**你我**（对举）
- 同一句里第二次当主语时**省略**而不是重念名字（「陈九看了看她，又低下头」）；
  换句子则重新给出名字
- 玩家的动作保持第一人称：你可以说「我把碗放下」，角色不行

**验证**：在第四轮那条长跑会话上直接看已有消息（不需要重新生成），最近 8 段动作里
含「我」的：**0 段**。抽样：`陈九把手从钩子上收回来`、`小满把怀里那本书换了个手抱，往旁边挪了半步`、
`陈九往道边让了半步，水都快没过鞋面了，抬手朝东边那条台级指了指`。

### 调用熔断（P1-9）

到本局上限时**只停生成之外的调用**，角色回复照常——聊到一半突然说不出话，
比多花几分钱糟糕得多。上限按世界存（`room.budget`），在运行时面板的「用量」页里改，
两个口径：额外调用次数（不依赖单价）与花费金额（要先填单价）。

**验证**（真机，同一局）：把「额外调用上限」设成 2（当时已用 9 次）→ 面板立即显示
「已熔断 · 还能再调 0 次」。

| 这一轮 | 结果 |
| --- | --- |
| 角色回复 | ✅ 照常生成（小满「胡记门口见。」，3.8k / 45 token） |
| 意图判断 | ✅ 跳过（没有「他这一轮想」那一行） |
| 一轮分析 / 摘要 | ✅ 跳过（账单里这两类没有增长） |
| 界面提示 | ✅ 「额外调用已到 2 次——这一轮只生成回复，不做意图判断与后台记录」 |
| 账单 | ✅ 12 → 13 次，只有「角色生成」+1 |

熔断只停**用户没直接要求**的调用。用户自己点发送的生成、以及副对话（世界管理员）
都属于主动操作，不受上限影响——这条是刻意的，写在 ROADMAP 的 P1-9 里。

## 五、召回评测（P1-11 的决策依据，2026-09-19）

P1-11 的原文是「**只有在 P1-10 证明关键词召回确实不足时才做**」向量检索。所以这一节
不是先写代码再找理由，而是先出题、再对答案。现在两份数据都跑完了，结论写在最后。

### 方法

一套「出题—对答案」的评测（`memory/recall-eval.ts` + `eval/recall-scenario.ts`）：
给定一批记忆与一批探针问题（每题写明该想起哪几条、不该出现哪几条），跑**真实的**
`recallMemories` + `selectWithinBudget`（与线上同一份代码），看四件事：

| 指标 | 含义 | 为什么关心它 |
| --- | --- | --- |
| 命题命中 | 该想起来的那条出现在排序里 | 漏掉线索 = 角色失忆 |
| 排名 | 它排第几 | 排到后面等于没想起来（预算只装得下前几条） |
| 进预算 | 800 token 裁剪后还在不在 | **这才是模型真正看得到的** |
| 串味 | 别人的视角混进来没有 | 比漏一条严重得多：那是角色知道了不该知道的事 |

### 一、合成题库（可复现，进仓库）

14 条记忆、9 道题（7 正 2 负），素材取自第四轮五十回合长跑里**被验证过**的线索：
三十箱没有清单的货、陈九船上的夹层、巷口那半堵新墙、秦娘赊出去的那壶酒、
小满的先生烧掉的鹿印货单、胡记上锁小屋的门牌。两道负向题专门测视角隔离
（秦娘在换场之后就不在戏里，门牌的事她不该知道）。

```
命中 100% · 进预算 100% · 串味 0% · 平均噪音 4.9 条 · 平均 349 token
```

这道题库是**回归红线**：改动召回打分时它会立刻报警。

### 二、真实数据（本机那局，214 条记忆 / 3 个角色）

合成题库只有 14 条，噪音压力太小；真正的考验是长跑跑了 50 回合之后的那 214 条。
用法：开发页 `http://127.0.0.1:5273/tools/recall-probe.html`——它从本机库读**真实记忆**，
用同一套内核实现跑探针，把表打出来（探针题目与判定规则就在 `apps/web/tools/recall-probe.ts`，
可改可复跑）。

| 探针 | 该答的人 | 视角内候选 | 命题排名 | 首条命中 | 进预算 |

**读出来的三件事**：

1. **该想起来的没有漏。** 六道正向题全部命中，而且排在第 1–2 名、全部通过了 800 token 的
   预算裁剪。也就是说：真实长跑数据上，关键词召回**没有出现「想不起来」的失败**。
2. **串味为零。** 秦娘那道负向题里，门牌的事一条都没有冒到她那边——视角隔离是结构性的
   （按 observer 过滤），不靠打分兜底。
3. **真正的问题在精度，不在召回。** 平均 5 条噪音意味着 800 token 里大约一半被
   **次相关**的条目占掉（同一件事在几十轮里反复出现，条目各写各的）。向量检索解决的是
   「换了说法、字面不重叠」的漏召回——这次一道都没出现；它不解决这类重复占位。

### 结论：P1-11 暂不做向量检索

按 ROADMAP 的约定（评测证明必要时才做），**证据不支持现在上向量**：没有一例漏召回，
而真正的开销来自重复条目的占位。所以 P1-11 以「评估完成、暂不做」收口，并写清触发条件：

> 当真实数据上出现**漏召回**（命题排名 > 3 或进不了预算）时，才引入向量。

替代方向记在 TASKS 里：**同类条目去重**（同一线索的重复记忆只留分数最高的那条，
预算就能让给别的线索）。它不需要嵌入模型、不需要额外调用，而且上面这套评测
可以直接量出它省了多少预算。

## 六、端到端对话测试

要跑完整的端到端（真的聊出内容、看着记忆累积），需要一个 OpenAI 兼容的接口。注意 **DeepSeek 网页版账号不含 API 额度**，需要单独在开放平台充值才能拿到 Key。

拿到 Key 之后在应用的「模型接入」面板填 `https://api.deepseek.com` 与模型名 `deepseek-chat`，就可以：

1. 导入两三张卡，让它们同场
2. 聊十几轮，中途让某个角色离场再回来——他应该不记得离开期间发生的事
3. 打开记忆面板，对照「客观经过」与各角色「眼中的事」，确认存在合理差异
4. 改一条记忆，确认下一轮角色按改过的版本说话
5. 重抽一次，确认该回合的记忆被撤销且没有留下残余
