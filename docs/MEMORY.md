# 记忆与长对话：现状、测量与方案

> 这份文档回答四个问题：① 500 条消息会不会出问题；② 什么时候提炼 / 压缩；
> ③ 新对话该带多少记忆、怎么带才不臃肿；④ 记忆怎么影响性格与情感、怎么回滚。
> 所有数字都来自本机实测（假模型、可复现），测量方法在最后一节。

## 一、结论先摆出来

| 问题 | 现状 | 该做什么 |
| --- | --- | --- |
| 500 条消息会不会「炸」 | **不会**。提示词从第 60 轮起封顶在 **3,754 字**（装配只带最近 40 条历史 + 记忆预算），300 轮实测 0 报错 | 不用为「上下文超长」改造装配 |
| 真正的问题是什么 | **记忆池线性膨胀**：300 轮 → **590 条记忆**（约 2 条/轮）。每次召回想带也带不了几条，于是「越聊越记不住真正相关的那条」 | 记忆**合并 + 索引化**（顺序 27），这是本主题的核心 |
| token | 300 轮合计 ≈ **170 万字输入 / 11 万字输出** ≈ **93 万 token ≈ 2.2 元**；平均每轮约 2,600 输入 + 190 输出 | 带记忆进新对话必须**按索引**，不能按全文 |

## 二、实测曲线（300 轮 / 601 条消息）

```
第 25 轮   消息  50 条   记忆  44 条
第 50 轮   消息 100 条   记忆  92 条
第 100 轮  消息 201 条   记忆 196 条
第 200 轮  消息 400 条   记忆 394 条
第 250 轮  消息 501 条   记忆 492 条
第 300 轮  消息 601 条   记忆 590 条      ← 页面上的错误块 0 个，页面级错误 0 条
```

**记忆 ≈ 2 × 轮数**（每轮一条客观经过 + 每个在场角色一条视角）。这既是这个产品的特色
（每个角色记的东西不一样），也是它的负担。

提示词长度（`generate` 调用）：

```
第  1 次 1001 字 → 第 31 次 1604 字 → 第 61 次 3733 字 → 之后一直在 3754 字上下浮动
```

**为什么封顶**：`assemble.ts` 只带**最近 40 条**历史（`historyLimit ?? 40`）+ 记忆召回按预算
挑几条。所以上下文不会无限涨——这是**好**的；代价是「40 条以前的事」只能靠记忆与章节回顾，
而它们现在有 590 条、没有层级。

## 三、什么时候提炼与压缩（问题②）

现在已有的三层（都在跑，各有节奏）：

| 层 | 何时跑 | 产出 | 实测频率（300 轮） |
| --- | --- | --- | --- |
| 一轮分析 | **每轮** | 客观经过 + 各角色视角（1 + N 条） | 322 次 |
| 分层摘要 | 每若干轮 | 「这一场到目前为止发生了什么」 | 42 次（约每 7 轮） |
| 章节回顾 | 场景结束时 | 一章一句话 | — |

要补的是**第四层：记忆合并（粗粒度印象）**。建议的触发线（第一版，之后按数据调）：

| 触发条件 | 做什么 | 为什么是这条线 |
| --- | --- | --- |
| 一条对话里**同一视角**的低重要度记忆（`importance ≤ 0.4`）超过 **40 条** | 把它们合并成 **1–3 条「印象」**（例：「这半个月他一直在替秦娘挡账房的事」） | 300 轮 590 条里绝大多数是这类「日常经过」，它们挤占召回预算却几乎不会被单独需要 |
| 一条对话超过 **120 条**记忆 | 全量跑一次合并，并按 20 轮一段生成时间线索引 | 120 条是「召回预算（几条）× 轮数」之间开始失真的位置 |
| 每 **40 轮**（或每 300 条消息） | 生成一条**阶段性印象**，同时刷新索引 | 与已有的分层摘要同频，避免另开一套节奏 |

**硬约束（三条，写在这里是因为它们决定实现对不对）**：

1. **合并只标「已被取代」，绝不删原文**。原文留在库里、仍能被面板搜到，
   合并出来的印象通过 `supersedes: EventId[]` 指回去——这是回滚与「这件事我记错了」的唯一依据。
2. **合并要按视角分开**：A 眼里的印象与 B 眼里的印象本来就是两件事，混起来会让角色失去差异。
3. **合并本身是一次模型调用**，所以要能省就省：只对低重要度、同一视角、时间相邻的记忆做，
   并且**在后台队列里跑**（用便宜模型），不能阻塞对话。

## 四、新对话带什么、带多少（问题③）

你的构想（**附件像文件夹、按关键词检索**）与这里的结论一致：**常驻的永远是索引，正文按需取**。

新对话开始时，把原对话的东西压成**三层**塞进角色卡附件：

| 层 | 内容 | 大小预算（第一版） |
| --- | --- | --- |
| ① 关系现状 | 一句话：这个角色此刻怎么看待玩家（由情感/关系状态生成） | ≤ 60 字 |
| ② 时间线索引 | 每章一行（章标题 + 一句话）+ 关键词 | ≤ 20 行 ≤ 600 字 |
| ③ 记忆索引 | 每条印象一行：**关键词 + 半句话**（不展开正文） | ≤ 60 行 ≤ 1,000 字 |
| 合计常驻 | | **≈ 1,600 字 ≈ 800 token** |

**为什么不臃肿**（用实测数字算）：590 条记忆全文 ≈ 4.7 万字 ≈ 2.4 万 token，不可能全带；
合并成 ~50 条印象后全文 ≈ 8,000 字（4,000 token）也还是贵。**索引化**之后 1,600 字封顶，
而命中的那几条正文（每次 2–3 条，≤ 400 字）在**对话里出现关键词时**才注入。

**「什么时候去搜」**（这正是你提的那条，也是最省 token 的一环）：

1. **关键词命中**：用户这句话里有索引里的关键词（「秦娘」「货栈」「那批货」），
   就把对应的 2–3 条正文注入本轮提示词；
2. **意图命中**：用户在问过去（「还记得吗」「上次」「以前」），同样触发检索；
3. **不触发就一点都不带**：日常闲聊只带 ①（关系现状）那一句——
   **这是省 token 的关键**，也是「记忆像文件夹」这个比喻真正的落地方式。

> 这一条与现有的混合召回（`core/memory/recall.ts`）是**同一条路**：
> 现在它按重要度 + 关联度从全量里挑；加索引之后，挑的范围从「全部 590 条」变成
> 「50 条印象 + 命中的原文」，精度与成本同时改善。

## 五、记忆对性格与情感的影响，以及回滚（问题④）

现状：每轮会推演情绪与关系（`memory/affect.ts`），写得进、看不出、也撤不干净。
建议三条：

1. **影响必须是「记录」而不是「直接改数」**：每次记忆影响性格/情感时，落一条
   `AffectChange { targetInstanceId, before, after, reason, sourceMemoryIds, createdAt }`。
   它只追加、不覆盖——**能不能回滚，取决于原来的值有没有被记下来**。
2. **回滚有两条粒度**：① 按轮回滚（已经有了：归档 / 重抽会回滚情绪与关系）；
   ② **按条目回滚**（新）：在记忆面板的「影响」里点「撤销这条影响」，
   把关系值改回 `before`，并把这条变更标成 `reverted`（不删，留痕）。
3. **不可逆的点只有一处**：`deletedAt` 的软删除与合并的「已被取代」——
   两处都保留原文，所以任何一条影响都能找到它的来源与当时的数值。
   UI 上要能一眼看到「这条印象是由哪几条记忆合并来的」。

## 六、拆成能做的步子（顺序 27a–27e）

| 顺序 | 做什么 | 为什么排在这儿 | 验收 |
| --- | --- | --- | --- |
| 27a | 记忆合并（合并低重要度、同视角、时间相邻的；原文标 `supersededBy`） | 记忆池是根，先收住它 | 内核单测 + 300 轮实测：记忆条数从 ~2/轮降到目标线以下，且随便点一条印象能找到原文 |
| 27b | 新对话的「记忆附件」（关系现状 + 时间线索引 + 记忆索引）并写进角色卡附件字段 | 有了印象才能生成索引 | 开新对话时附件 ≤ 1,600 字；索引里能看到原对话的线索 |
| 27c | 关键词触发的按需检索（索引命中 / 意图命中才注入正文） | 附件不臃肿的前提 | 日常闲聊的提示词**不增长**；提到关键词时对应正文出现在提示词里 |
| 27d | 影响记录与按条目回滚 | 有了它才敢让记忆改性格 | 面板能撤销一条影响，关系值回到 `before` |
| 27e | 面板与文档（索引视图、印象的来源链、TASKS/EVAL 记录） | 收尾 | 真机走一遍：老对话 → 建附件 → 新对话提到旧事 → 角色接得上 |

**为什么先 27a**：另外四步都以「记忆有层级」为前提；不做合并，索引就是把 590 条平铺一遍，
照样臃肿。而且 27a 一个人也能验（单测 + 长跑数字），不依赖界面。

## 七、测量方法（可复现）

```bash
# 1) 本机起开发服务器与假模型（零成本、可重复）
cd apps/web && node node_modules/vite/bin/vite.js --host 127.0.0.1 --port 5273 --strictPort
node tools/fake-model/server.mjs --port 5280            # stderr 上会打每次调用的提示/输出字数

# 2) 脚本：导入一张卡 → 配假模型 → 连着发 N 句（每句等回复落盘再发下一句）
node <验证目录>/measure-long.mjs 300

# 3) 汇总：按调用类型统计提示/输出字数，并画出 generate 的增长曲线
```

这次的三条读数（都写在上文）：**提示词第 60 轮封顶 3,754 字**、
**记忆 2 条/轮线性增长**、**300 轮 ≈ 93 万 token ≈ 2.2 元**。

**注意**：假模型返回的是固定台词，所以这三次测量量的是**装配与后台**（提示词、记忆、
token），不能用来判断「角色有没有跑偏」。后者要靠真模型的定向测试（见 EVAL 第十节那种）。
