## 1. P0：立即处理

### A1 本地助手可被任意网页冒用

- **位置**：`tools/local-bridge/server.mjs:58-63`、`223-278`。
- **现状**：监听 127.0.0.1，但返回 `access-control-allow-origin: *`，无令牌，不查 Origin 和 Host。第 59 行注释说"只允许本机页面"，与代码矛盾。
- **失败场景**：助手运行期间，用户打开任意恶意或被入侵的网页。其脚本可以 POST `http://127.0.0.1:8791/ask`，用用户的 DeepSeek 登录态发任意内容并读回复；可读 `/health` 获知当前标签页 URL；因为不校验 Host，DNS rebinding 同样可行。
- **方案讨论**：
  1. **Origin + Host 白名单**。只放行正式站点和本机开发端口；Host 必须是 `127.0.0.1:PORT` 或 `localhost:PORT`。改动十几行，零体验成本，挡住浏览器发起的攻击。缺点是挡不住本机其他进程，但本机进程本来就能直接操作 9222 调试端口。
  2. **随机配对令牌**。启动时打印令牌，用户粘贴进应用，请求带 `Authorization`。防御更完整，多一步配对。
  3. **推荐**：立即做方案 1，同时补 A13 的上限；方案 2 作为后续增强。修复时顺带补一个 Origin 校验测试。

## 2. P1：同步正确性与公网安全

同步是项目的底线。A2 到 A6 共同指向一个事实：**当前同步在若干常见时序下会静默漏数据，而界面显示"两端一致"**。建议把它们作为一个整体修复批次，一起补测试。

### A2 Service Worker 缓存了同步接口

- **位置**：`apps/web/public/sw.js` 约 113-160 行；同步客户端 GET 调用见 `packages/core/src/sync/http-client.ts:137,153,164`；同步地址为本站 `/sync`（`lib/account-auth.ts:34`）。
- **现状**：SW 只放行非 GET 与跨域请求。其余同源 GET 一律缓存优先，并对 `ok` 响应 `cache.put`，匹配时 `ignoreVary`。Cache API 不看 `Authorization`，也不看 Cache-Control。
- **失败场景**：`/sync/spaces/x/head` 首次成功后永远命中缓存，本机永远认为远端没变。`pull?since=N` 在游标不变时永远返回同一页。数据以明文留在 Cache Storage，退出登录或删除账户后仍在。
- **方案讨论**：
  1. 黑名单：`/sync` 前缀直接 `return`。一行修复，但以后新增接口仍可能中招。
  2. **白名单（推荐）**：只缓存 `/assets/*`、图标、manifest、`index.html`。需随资源目录维护，但从根上杜绝缓存 API。
  3. 无论哪种，都必须 bump `CACHE` 版本号，让已污染的缓存在 activate 时清除。已部署的用户只有上线新 SW 后才会恢复，部署需要用户决定。
- **测试**：用 fake 请求验证 `/sync/*` 不进入缓存。

### A3 拉回的记录推进了 `pushedAt`

- **位置**：`packages/core/src/sync/loop.ts:231`；`repository.ts:706` 按 `updatedAt <= since` 过滤。
- **失败场景**：推送后、拉取前，本机写入一条 `T1`。同轮拉回另一设备的 `T2 > T1`。`pushedAt` 被推到 `T2`，下一轮 `since: T2` 跳过 `T1`，这条永远推不上去。
- **方案讨论**：
  1. **`pushedAt` 只由本机推送成功的记录推进（推荐）**。拉回的记录写入本地时，保留它自身的 `updatedAt`，下次推送若与远端 `(id, updatedAt)` 相同就跳过。改动集中在 `loop.ts`，首次同步后最多多推一趟，无害。
  2. **脏标记**：写入时置脏，推送成功清除。语义最清晰，但每个写路径都要维护标记，还需迁移。
  3. 推荐方案 1，配套测试"推拉之间插入本地写 + 对端时钟超前"。

### A4 服务端重建或快照恢复后游标不重置

- **位置**：`loop.ts:84-87` 只在 `spaceHandle` 变化时重置；`apps/web/src/lib/sync.ts:377-400`、`624-653`。
- **失败场景**：服务器库丢失后重连，handle 不变。本地 `pushedAt` 仍是旧最大值，一条都不推。本地 `pulledHead` 为 5000，新空间从 0 开始，对端推上来的前 5000 条本机永远拉不到。
- **方案讨论**：
  1. `runSync` 发现 `serverHead < pulledHead` 时，清零 `pulledHead` 与 `pushedAt` 全量重来。这是自愈式检测，覆盖所有未知原因。
  2. `connect` 的新建分支、`restoreSnapshot` 完成后显式重置状态。这是确定性修复。
  3. **两者都做**。代价仅是一次全量推送。更进一步可以给空间加一个服务端生成的 `epoch`，客户端记住它，不一致即重置，能覆盖"重建后 head 恰好又涨过旧值"的情况。

### A5 归档对话绕过逻辑时钟

- **位置**：`packages/core/src/storage/repository.ts:1069`。
- **现状**：直接写墙钟 `updatedAt: at`，其他写路径都走 `stampUpdatedAt`。
- **失败场景**：水位线因对端时钟超前而高于本机时间时，归档记录 `updatedAt <= since`，永远推不出去；或被对端旧状态按"后写者赢"压回。结果本机已归档、记忆已回滚，其他设备上对话仍活着。
- **方案**：改为 `await this.stampUpdatedAt(COLLECTIONS.conversations, id, at)`。无副作用。顺带全局 grep 所有直接写 `updatedAt:` 的地方，确认没有第二处漏网。可考虑加一条 lint 规则或单测守护。

### A6 `deletedAt` 不在 AAD 保护范围内

- **位置**：`packages/core/src/crypto/records.ts:52-54`；`loop.ts:197-204`；`repository.ts:749-754`。
- **失败场景**：恶意服务端保持密文与 `updatedAt` 不变，只改线上明文 `deletedAt`。解密正常通过，`merge.ts:29` 在时间戳相同时"墓碑赢"，本地记录被删；反向操作可复活已删记录。
- **方案讨论**：
  1. **只信任解密后的 `value.deletedAt`**，并校验与线上字段一致，不一致就拒收。不需迁移，推荐先做。
  2. 把 `deletedAt` 纳入 AAD，采用 `v2|` 前缀并双读兼容。更严谨，但所有旧密文需要在下次写入时逐步升级。
  3. 前提是墓碑的密文里确实包含 `deletedAt`；若墓碑当前不带密文，需要先让墓碑也封一个小密文。SYNC.md §3.3 应补充说明威胁模型。

### A7 字节配额可绕过

- **位置**：`packages/core/src/sync/server.ts:358`；`http.ts:96-117`、`128-134`；`tools/sync-server/src/main.ts:127`。
- **现状**：配额只算 `sealed`。`id`、`updatedAt`、`deviceId` 无长度限制，`keyWraps` 是任意对象。请求体上限 8MB。
- **失败场景**：匿名建空间后，每次 push 塞超长 id 的小记录，每分钟约 120 × 8MB，很快写满磁盘。
- **方案**：
  - 字段校验：id ≤128 且限定字符集；`updatedAt` 必须是 ISO 且 ≤32；`deviceId` ≤64；`keyWraps` 只允许 `{password, recovery}` 且整体 ≤2KB。
  - 配额按整行字节计算，并统一 `spaceUsage` 与 `recordSize` 的口径。当前一个统计 base64 长度、一个统计解码后字节，实际上限约为配置值的 75%。
  - 请求体上限可降到 1-2MB，客户端分批。

### A8 `X-Forwarded-For` 取第一跳

- **位置**：`tools/sync-server/src/main.ts:189-195`；`deploy/nginx-8443.conf.example:42`。
- **失败场景**：nginx 示例用的是追加，攻击者自填首跳即可每请求换桶，建空间限流失效。刷满 `maxSpaces=10000` 后，所有新用户建空间返回 503。
- **方案**：服务端改取 `X-Real-IP`，或 XFF 最后一跳；nginx 示例改为 `proxy_set_header X-Forwarded-For $remote_addr;`。最好加一个"信任代理跳数"配置，默认 1。同时处理 C 节中限流 Map 不清理的问题。

### A9 建空间无密码强度下限

- **位置**：`apps/web/src/lib/sync.ts:368-369` 只检查非空；换密码时才要求 ≥6 位（`sync.ts:544`）；`http.ts:213-224` 无凭证即返回 `keyWraps` 与 `credentialHash`。
- **失败场景**：句柄可由 id 推出，id 常是手机号或昵称。取得 `passwordWrap` 后离线跑 PBKDF2 字典，弱密码很快被破，所有聊天与同步的 API Key 暴露。
- **方案讨论**：
  1. 新建分支强制最小长度并给强度提示，与换密码一致。成本最低。
  2. 元数据接口不返回 `credentialHash`，加入方用不到它。
  3. 更彻底：取回 `keyWraps` 也需要一次凭证握手，或者对该接口做严格的每句柄限流。这会改变协议，需要评估旧客户端兼容。
  4. 长期可考虑把 KDF 升级为 Argon2id（WASM），抗 GPU 更强，但增加包体。

### A10 providers 对齐 effect 无限循环

- **位置**：`apps/web/src/lib/providers.ts:217-263`。
- **现状**：effect 依赖 `profiles`，内部每次从 IDB 读出新数组并 `setProfiles`，引用变化再次触发。`cancelled` 拦不住 `setProfiles`。
- **失败场景**：同步就绪且至少一个配置时，根组件持续重渲染并反复读 IDB。手机耗电发热、输入卡顿，还可能反复触发凭据同步。
- **置信度**：中高，静态推理。建议先用 React Profiler 确认 commit 次数。
- **方案**：
  1. 内容比较一致就不 set。最小改动。
  2. **拆分 effect（推荐）**：读远端 profiles 只依赖 `sync.status` 和 `db`；依赖 `profiles` 的凭据逻辑单独一个 effect。更清晰，需要理顺 `activeId` 更新顺序。

### A11 导入封存不改写内部引用

- **位置**：`packages/core/src/storage/archive.ts:264-375`。
- **漏改写的引用**：
  - `stateSnapshot[].instanceId` 及关系 `target`：导入后归档，状态回滚匹配不到任何角色，但记忆和章节照删。
  - `MemoryEvent.supersedes` / `supersededBy`：印象溯源失效，被取代的原文永远召回不到。
  - `scene.recapUpToMessageId`：退回序号比较，而导入后序号重新从 1 开始，未覆盖的消息被误判为已覆盖并从提示词消失。
  - `AffectChange.sourceMemoryIds`、`artifacts[].targetId`。
  - 章节 `createdAt` 全部设为同一时刻，章节顺序不确定。
- **方案**：先建 `memoryIds`、`messageIds`、`instanceIds` 三张映射表，再统一改写所有引用字段；章节保留原 `createdAt`；`recapUpToSeq` 按新序号重算。关键是补一条"导出→导入→归档/召回/场记收起"往返测试，否则以后新增引用字段还会漏。可以考虑在类型层面给 id 字段加品牌类型，并用一个集中函数枚举所有引用字段。

### A12 预算守卫 O(n²)（推算）

- **位置**：`packages/core/src/prompt/budget.ts:52,55,62-66`。
- **现状**：`used()` 每次重算全部块的 token；丢历史时每丢一块调一次 `used()` 并 `filter` 整个数组。
- **失败场景**：`full` 历史策略或摘要没跑，3000 条历史远超 65536 预算，需丢两千多块，主线程卡数秒；多角色时每个发言者都要装配一次。
- **方案**：每块 token 数缓存一次，维护累计总量，丢块时相减，`drop` 用 Set 标记；或对历史做前缀和后二分截断点。输出不变，复杂度降到 O(n) 或 O(n log n)。先写一个 3000 条的基准测试再改，改后对比输出快照一致。

### A13 本地助手缺输入上限

- **位置**：`tools/local-bridge/server.mjs:72-76`、`256`。
- **方案**：请求体限 1MB；`timeoutMs` 夹在 5 到 600 秒；同一时刻只允许一个 `/ask`，其余排队或返回 429，否则并发会互相覆盖输入框。另在文档中说明 9222 调试端口等于交出整个浏览器，必须用独立 `--user-data-dir`，用完即关。

### A14 CI 覆盖缺口

- **位置**：`pnpm-workspace.yaml` 不含 `tools/*`；`.github/workflows/ci.yml` 不跑 `build:sync-server`；`apps/web/tsconfig.json:8` 不含 `tools/**`。
- **失败场景**：线上服务端代码坏了 CI 仍然全绿。
- **方案**：CI 增加 `pnpm build:sync-server` 与 `apps/web/tools` 类型检查；给同步服务端补一个 HTTP 冒烟测试，覆盖鉴权、请求大小、配额、并发冲突。这也是 A7、A8 修复的验证手段，应当先于它们落地。

### A15 部署模板缺安全响应头

- **位置**：`deploy/nginx-8443.conf.example:14-46`、`deploy/Caddyfile.example`。
- **现状**：无 HSTS、CSP、`X-Content-Type-Options`、`Referrer-Policy`、`frame-ancestors`。这是端到端加密应用，密钥就在浏览器里。
- **方案讨论**：
  - `script-src 'self'` 成本低且收益最大，也同时缓解 B18。
  - `connect-src` 难点在用户自定义模型地址，可先用 `connect-src 'self' https: http://127.0.0.1:*`。
  - nginx 中 `location = /sw.js` 的 `add_header` 会让它不继承 server 级头，需在该 location 重复，或统一放 include 文件。
  - 先用 `Content-Security-Policy-Report-Only` 观察一段时间再切正式。上线需用户决定。

## 3. P2：功能错误与潜在异常

### B1 同设备并发同步
- **位置**：`apps/web/src/lib/sync.ts:348,417,429-448`；`packages/core/src/sync/auto-sync.ts:76-80`。
- **问题**：立即同步、启动同步、连接同步都绕过自动同步的互斥，两个循环交错推送并互相覆盖状态，叠加 A3 更易漏推。`flush()` 在运行中只设 `dirty` 就返回，调用方误以为已同步。
- **方案**：所有入口走同一个串行队列；`flush` 等当前轮与补跑轮都完成。与 B3 一起考虑用 Web Locks 做跨标签页互斥。

### B2 后台任务无退避
- **位置**：`apps/web/src/lib/worker.ts:524-601`；`packages/core/src/platform/background-runner.ts:124-129`。
- **问题**：断网、429、Key 暂空时，同一任务几毫秒内连败 3 次，被永久标 `failed`，本轮记忆与情绪分析丢失且无恢复入口。
- **方案**：加 `nextAttemptAt` 指数退避；配置类错误不计次数，直接停止等待下次触发；一轮 drain 跳过本轮失败过的任务；UI 提供"重试失败任务"入口。

### B3 多标签页重复执行任务
- **位置**：`background-runner.ts:95-111`，先 list 再 put，无比较交换。
- **问题**：两个标签页同时认领同一任务，模型调用两次、账单两笔、情绪可能叠加两次。
- **方案**：用 `navigator.locks` 保证同一时刻只有一个标签页 drain，实现最简单；或在单个 readwrite 事务里"读到 pending 才改 running"。推荐 Web Locks，并让情绪推演的幂等检查在写入时再做一次。

### B4 印象被连带删除
- **位置**：`packages/core/src/memory/consolidate.ts:279`；`repository.ts:1552-1558`。
- **问题**：印象继承整组 `sourceTurnIds`。重抽或删除其中任一回合，印象被软删，但其余原文仍带 `supersededBy` 且已设 `consolidatedAt`，这些回合的记忆在召回中一起消失，也不会再合并。
- **方案讨论**：
  1. 删除印象时"撤销合并"：清除原文的 `supersededBy` 与 `consolidatedAt`，让它们重新参与召回与合并。语义正确，推荐。
  2. 只从印象摘掉该回合来源，不删印象。实现简单，但印象内容里仍含被删回合的信息，语义不纯。

### B5 读 Key 竞态
- **位置**：`apps/web/src/lib/providers.ts:173,180`。
- **问题**：`store.get(...).then(setApiKeyState)` 无取消保护。快速切换配置时旧请求后返回，把 A 的 Key 写入当前状态，请求带着它发往 B 的服务商，等于把密钥泄露给第三方。`encrypted` 档位风险更实际。
- **方案**：effect 内加 `cancelled` 并在 cleanup 置真，或写入前比对 `profile.id`。成本极低，建议与 A10 一起修。

### B6 管理员草稿整条替换
- **位置**：`packages/core/src/admin/tools.ts:264-280,334-342`；`repository.ts:1281-1284`。
- **问题**：修改已有卡时以空白卡为底，模型没传的开场白、示例对话、tags、`createdAt`、`source` 全部丢失。世界书的 `createdAt` 被重置、`extensions` 清空、条目 id 重新生成。`alternateGreetings` 在参数表里但 schema 未声明。旧草稿采纳时会覆盖之后的手动修改。
- **方案**：有 `cardId` 时以现有卡为底做字段级合并；约定显式空串表示清空；采纳前展示 diff 并校验 `updatedAt`，过期草稿提示冲突；补全 schema。

### B7 重抽"失忆"
- **位置**：`apps/web/src/hooks/useTurnRunner.ts:738-745`，对比发送路径 `522-545`。
- **问题**：重抽不传 `memories`、`intent`、`mentionText`，召回退化为空。
- **方案**：把召回抽成共用函数；意图默认复用原消息，若希望重抽重新判断意图，代价是多一次调用，可做成设置项。

### B8 世界书条目 id 冲突
- **位置**：`useTurnRunner.ts:211`；`assemble.ts:421,428`；`budget.ts:52`。
- **问题**：SillyTavern 导入的 uid 常是 "0"、"1"。两本书都生成 `worldbook:0`，丢块时一起丢，优先级 Map 被覆盖，React key 重复。
- **方案**：块 id 改为 `worldbook:${bookId}:${entryId}`，`WorldBookMatch` 带上 `bookId`。会改动提示词检查器与测试快照。

### B9 多币种相加
- **位置**：`packages/core/src/storage/usage.ts:162-166`。
- **方案**：按币种分组累加，主显示取出现最多的币种，其他列为"另计"；不做汇率换算，避免引入外部数据源。

### B10 流式失败边角
- **位置**：`packages/core/src/provider/openai-compatible.ts`。
- 非流式回退未检查 `json.error`，非 JSON 响应抛 SyntaxError 而非 ProviderError（334-348）。有些网关 200 返回错误体，会落库空回复。
- 未知 `finish_reason` 一律当失败（225），`eos`、`end_turn`、`STOP` 等会丢掉正常回复。建议只拦 `length` 与 `content_filter`，其余记警告。
- `finally` 只 `releaseLock` 不 `cancel()`（253-255），上层提前退出时服务端继续生成并计费。
- 多行 `data:` 逐行解析不合规范（355-373），影响小。
- **方案**：逐条修正并补测试。空回复在落库前统一拦截报错，作为兜底。

### B11 每次写入全量读房间（推算）
- **位置**：`repository.ts:1209-1232,1393-1418`；`director/scheduler.ts:337,345`。
- **问题**：`loadRoom` 读整个世界所有对话的消息与记忆并排序，每轮收尾调 7-10 次；`listMessages` 先全读再 slice；`turnsSinceLastSpoke` O(n²)。
- **方案**：按 `(collection, conversationId)` 建索引，`loadRoom` 只加载当前对话；一轮内缓存房间快照；`turnOrder` 用 Map 存下标。先补基准再改。

### B12 token 估算偏低
- **位置**：`budget.ts:14-20`。
- **方案**：每条历史加固定 3-4 token 开销，计入小节标题、at_depth 附加 system 消息与 tools 定义；预留 5% 安全余量。

### B13 IndexedDB 升级阻塞
- **位置**：`apps/web/src/lib/db.ts:503`。
- **方案**：`blocking` 回调里 `db.close()` 并提示刷新；`blocked` 回调给出"请关闭其他标签页"。下次升库版本前必须完成。

### B14 localSeq 与 stampCache
- **位置**：`repository.ts:623,1171-1193`。
- **问题**：发号先读后写，并发追加会重号，影响排序与场记游标。stampCache 不跨标签页失效，可能盖出不大于水位线的时间戳，引发 A5 同类问题。
- **方案**：发号放入同一 readwrite 事务；stampCache 用 BroadcastChannel 失效，或每次写前读水位线。与 B3 的 Web Locks 可共用一套机制。

### B15 PNG 解压
- **位置**：`compat/sillytavern/inflate.ts:43`；`png.ts:193`。
- **方案**：流式解压，超过 8MB 中止；非 `chara`/`ccv3` 块解析失败只记警告并跳过。

### B16 换密码不换主密钥
- **位置**：`packages/core/src/crypto/keys.ts:392-407`；`sync/sqlite.ts:300-312`；备份默认保留 30 份。
- **问题**：旧密码泄露后换密码，拿到旧备份仍能解出当前主密钥。"换密码即断开设备"只在鉴权层成立。

## 5. 横向问题与根因讨论

1. **同步的"水位线"模型过于脆弱**。A3、A4、A5、B14 都源于同一个设计：用单一时间戳 `pushedAt` 判断"哪些该推"，而时间戳同时受本机时钟、对端时钟、拉取结果影响。长期看，建议改为"本地变更序号 + 已推送序号"，即每次本地写入分配单调 `localSeq`，推送游标只看它，与墙钟彻底解耦。这是较大的重构，但能从根上消除这一类漏推。短期先用第 2 节的点状修复止血。

2. **缺少跨标签页协调**。B1、B3、B13、B14 都是多标签页或并发入口问题。建议统一引入一个基于 `navigator.locks` 的小工具，给同步、后台任务、发号、升库共用。

3. **引用完整性无集中保障**。A11、B4、B6 都是"改了一处 id 或结构，其他引用没跟上"。建议集中维护"每种记录有哪些引用字段"的表，导入、删除、合并都从这张表派生，并配往返测试。

4. **性能对长对话没有基准**。A12、B11 都是推算。建议先建一个 3000 条消息的合成世界，作为装配与收尾的基准测试，放进 CI 并设阈值。

5. **测试集中在 core，边缘几乎为零**。web 仅 8 个测试；sync-server、local-bridge、部署脚本无测试。线上风险最高的恰恰是这些边缘。

## 6. 建议修复顺序

每一步都能独立构建、测试、提交，符合"每步能构建测试提交"的约定。

1. **第一批（安全止血）**：A1、A13。改动小、收益最大。
2. **第二批（CI 基础）**：A14、B21。给后续服务端修复提供验证手段。

5. **第五批（公网加固）**：A7、A8、A9、A15、B19，涉及线上配置，部署由用户决定。
